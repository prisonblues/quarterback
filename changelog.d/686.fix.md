# two comments that justified themselves with claims about the code that were not true

Both found by a different-vendor second opinion on merged PRs, and both are documentation rather than
behaviour: nothing here changes what any dial resolves to or what any function does.

### `run()`'s signature (#687)

The comment explaining why `no_pr_claim` is last and keyword-only said "every caller here passes the
first fourteen positionally, and a parameter inserted mid-list silently shifts `escalated` into it."

Neither half held. The suites call `run()` with two positional arguments and the rest by keyword, so
a mid-list insertion would not touch them. There is exactly one long positional caller — `main()` —
and it passes **twenty**, not fourteen, before naming `no_pr_claim` by keyword.

The conclusion was right and stays. The reasoning under it described a codebase that is not this one,
which is worse than no comment: the next person to add a parameter reasons from it about their own
call sites. It now says what is there. The argument took three attempts to state correctly, and the count is the
reason: **five** of the signature's boundaries are type-silent — `post`/`json_out`,
`force`/`no_code_access` and `new_cycle`/`no_pr_claim` (bools), `scope`/`since` (strs) and
`narrowed`/`acknowledge` (`list[str] | None`). An insertion at any of the five passes every type
check. `narrowed`/`acknowledge` is the worst, not because of the type but because they are two
registers of the same shape: a swap sends escalated keys to the acknowledgement door, and both doors
accept the other's keys without complaint.

### `min_fix_growth_chars` and the empty string (#686)

The docstring explains at length why `0` is refused — "the OFF position written in a spelling that
does not say so, and `null` is already that spelling" — which reads as though `null` were the only
off spelling. A reviewer read it that way and reported `""` as an undocumented second off-switch
specific to this dial.

It is not specific to it. **Every** dial resolver in `panel_seats.py` reads `""` as null — all
seventeen, no exception — so refusing it on this one key would make it the only dial in the file that
answers an emptied value differently from every other. The fix is the docstring, not the resolver.

Stated as "every" rather than as a count on purpose. Three drafts of this paragraph each carried a
different number (sixteen, seventeen, twenty-two) because the answer moves with what you grep for:
`== ""` catches string comparisons that have nothing to do with dials. "Every resolver, no exception"
is checkable against the list of resolvers and does not.

Why the convention exists is **not** recorded anywhere, and the docstring now says so rather than
inventing a reason. It took two attempts to stop inventing one. The first asserted the convention was
the board's clear path; that is false, because `POST /dials/clear` stamps `cleared_at` and the dial
then resolves as *absent*, which is a different answer from `null` here. The second said the only
route that delivers a `""` is a hand-written `.harness-rules`; that is also false, because `POST
/dials` `json.dumps`es whatever `value` it is handed and stores it, validating the dial name and the
payload size but not the value's type. Both routes reach the resolver; only `clear` does not.
