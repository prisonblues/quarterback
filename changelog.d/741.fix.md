# the shared-tree guard reads the tree the command runs in, not the one you are standing in

`cd elsewhere && git checkout -- file` named no tree, so the guard substituted the session cwd
and judged the command against a repository it never opened — refusing a safe restore in one
repo over an untracked file in another, and, pointed the other way, waving `cd <shared tree> &&
git reset --hard` through from a private worktree. A literal `cd` in an earlier clause is now
resolved into the clause's working directory. Where that `cd` cannot be read — a `$VAR`, a glob,
a `$(…)` — the guard asserts nothing about any tree rather than assuming the session's.

A bare `--` no longer makes `git checkout` unconditionally destructive: it is a disambiguator,
not a scope, so `git checkout -- one-file.txt` is now weighed as the named path it is, while
`git checkout -- .`, an operand that is a pathspec rather than a filename (`-- '*'`, `-- ':/'`,
which restore the whole tree), and a `--` with no operands keep their verdict.

Two things this gives up, both measured and both pinned by tests. `git checkout -- <a literal
path that is not on disk>` is no longer refused, and one of those is a tracked file a peer deleted
without committing, which the checkout puts back. And a `cd` the reader cannot resolve now
silences the shared-stash gate as well as the two tree gates — `cd "$D" && git stash pop` was
refused before — because a command whose directory cannot be read is one whose repository cannot
be read either.

The literal `cd` is the only thing that came off the guard's documented not-chased list, and it
came off because it is not the same kind of entry: `env`, `sudo`, a `$VAR` target, aliases, shell
functions and `xargs` are an adversary spelling around a static reader, while `cd elsewhere && …`
is the fleet's ordinary idiom for multi-repo work. Those all stay where they are.
