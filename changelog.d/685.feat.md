# `prune-worktrees --finished`: which live worktrees are done, answered by the script

Every category the sweep reported was about a worktree that is already gone. The question
before it — of the ones still registered, which can go? — existed only as prose in
`/tree-shake`: four shell one-liners an agent re-derived each run, finished only with a
human present to answer the question at the end. So it ran rarely, and the one sweep that
clears landed work was the one nobody ran. Measured on 2026-09-06, one lexray checkout:

```
78 registered worktrees          29 <project>-* siblings, 28 under .claude/worktrees,
                                 7 wt-NNNN, 14 under /tmp
12 GB under .claude/worktrees    Claude Code's subagent trees, invisible to every sweep
1 PR merged in July              still standing, with its containers
826 orphan test databases
```

`--finished` is that classification as a script. It walks every registered worktree —
not only the `<project>-*` siblings the rest of the file is about — and prints three
buckets, then exits. Nothing in it removes anything; `remove-worktree` stays the only
thing that tears a worktree down, and a `--prune` or `--remove-*` flag beside `--finished`
is refused rather than ignored. `--porcelain` gives `/tree-shake` a row per tree.

### the rule is wider than "PR merged", and by measurement it had to be

"Merged" found one finished sibling in 29. The rest of what had landed, GitHub records as
CLOSED, and the old rule read CLOSED as in-progress:

| the PR | what happened | the rule that sees it |
|---|---|---|
| #1139 | all 24 commits reached `test` via an omnibus merge | head reachable from another remote branch (#700) |
| #1627, #1607 | "Superseded by #1829", rebased onto current `test`; #1829 merged | `Superseded by #N` in a closing comment, #N merged |
| #1541, #1545 | fix re-landed from a different branch | a human decides — reported as such, not as finished |
| 21 subagent trees | no PR; tips sitting on the pushed `fca` feature branch | no PR, tip reachable from a remote branch |

The question each rule asks is loss, not tidiness: `remove-worktree` deletes only the
*local* branch, so a tip reachable from any remote ref loses nothing. The post-PR check
keeps `--not --remotes` for the same reason, and the `cat-file -e` guard before it — with
the object absent `git log` fails and a bare `| wc -l` reads 0, "nothing to lose" on
exactly the branch nobody can vouch for.

### `cannot-verify` is its own bucket

A `gh` that did not answer, a head SHA this repository has not fetched, a board that could
not be asked, a detached HEAD: each is "no answer", and the doctrine from #244 and #735 is
that no answer must not read as a clean one. A held tree is in-progress whatever its PR
says, with the holder named — a merged PR does not mean nobody is in there.

### each row says which teardown applies

Only a `<parent>/<project>-<name>` sibling has a create-name for `remove-worktree` to
resolve. An agent tree under `.claude/worktrees` or a scratch tree under `/tmp` was never
given containers, a database or a port, and `git worktree remove` is the teardown; the
row says so, so `/tree-shake` no longer has to work it out — or skip them, which is what
it did.

`/tree-shake` §1 now reads the report instead of restating the rule, which was the second
half of #685: a skill restating a script's logic in prose is a second copy of that logic,
and the two can disagree without anything noticing.
