# finished work leaves the top of the plan by itself, on the one fact that is not a judgement

Picking work up writes a plan item (#427) — *"picking work up is the one act that
should put it on the board, and the only one that doesn't"*. Putting it down was
never wired: `plan_done` appears in exactly one brief (`/get-involved`), and
`/fix-issue`, `/fix-and-land`, `/fix-and-review`, `/epic`, the dashboard's ⚒ and
`qb-start` all create the item and none of them closes it.

The two halves then decay differently, which is what makes the residue permanent. A
claim expires on its TTL and needs nobody; a plan item has no TTL at all. So every
issue worked through any route but `/get-involved` leaves an `open` row for ever —
and it lands at the **top**, because picked-up items rank first.

Measured twice. On this repo, ranks 1, 2 and 3 were closed work (#539, #528, #533),
all still `state: open`, all still holding a claim, each flagged `done_candidate`
and re-confirmed by `qb-reconcile` every fifteen minutes for days. On lexray, ranks
1–13 were all `rank_source: "picked-up"` with `counts.claimed: 0` — thirteen pickup
artifacts in front of a thirty-one-item human-ordered plan, so a reader taking
`next` at face value got finished work and a human scrolling the board saw the
ordered plan pushed below the fold. `next.caveat` described the residue accurately;
at thirteen items the description is the thing you have to read past.

The predicate has been correct the whole time. What was missing was an actor.

### The rule that changed, and how far

`qb-reconcile` said "it NEVER edits the plan: 'this item looks done' is a candidate
for a human or a `plan_done` call, not a state transition to make behind their
back". That is narrowed, deliberately and as an amendment rather than a flag
somebody slipped in: **it never *judges*.** `--apply` completes an item whose own
ref is a pull request GitHub reports `MERGED`, and nothing else. That the work
merged is a fact about the code; recording it is bookkeeping. `dropped` stays a
decision the plan's model keeps apart from `done`, and nothing infers one.

### Why only the PR leg

The decided predicate is three-legged — an item is done when its PR merges, or its
issue is closed, or the agent releases it — and `MERGED` is the only leg that is
**base-branch agnostic**. GitHub says `MERGED` whatever the base, so a PR that
landed on `test`, or on an `fca` integration branch two merges below it, completes
its item with no change at all. On lexray's plan as it now stands that is 31 of 32
items.

A closing keyword only fires on a merge into the repository's *default* branch, and
an item whose ref is an **issue** cannot see the pull request that implemented it —
the item→PR edge is computed on every pass and stored nowhere (#396). And the
trailers are not uniform: of thirteen lexray items landed on `fca`, ten carried
`Fixes #N` and two carried only `Refs`, so an actor keyed on "the issue closed"
would leave those two on the plan for ever on a branch that had already landed the
work. So an issue-ref `done_candidate` is **declined by name, in the report, on
every tick** — the residue that leg would clear stays readable until #396 makes it
answerable, rather than being cleared on a signal that does not mean the same thing
in every repo.

### What holds it to that

Three properties, and each is a way this could have gone wrong quietly.

**The merge is re-read from GitHub at the point of the write.** `CONDITIONS` is a
vocabulary five checks share and any of them may legitimately widen; an actor
trusting the label would one day complete an item on a fact nobody had checked, on
a fifteen-minute timer. A `done_candidate` whose state is not `MERGED` is declined
with the disagreement quoted.

**A run that could not reach GitHub writes nothing**, and that falls out rather
than being special-cased: an unresolved ref is an `unknown` and raises no finding at
all, so the same property that stops an unmade check reading as a clean one stops it
reading as a merge.

**A refused write is reported and raises the exit code.** A 409 is the board holding
a rule this pass must not route around — "a human dropped this item" is the one
state `done` refuses — and a rule enforced into a silence is a rule nobody learns.
It is not filed as an `unknown`: nothing went unchecked, something went undone, and
`complete` still describes the checks.

Two smaller ones. A claim the board **left** standing is named in the report, since
`done` releases only the caller's own claim and this pass calls with a machine token
and no session — a row that went done under somebody's hand is the one row a reader
may want to ask about. And an item this pass completed is withdrawn from the
`/plan/reconcile` hand-off, because those rows tell a reader that an *open* item
looks finished, and a completed one would carry "looks done" for ever: `run` reads
open rows only, so nothing would ever find it again to withdraw it. A write that
*failed* keeps its finding.

### Where it runs

The shipped unit is now `qb-reconcile --apply --post --quiet`. The timer is what
carries the actor, because it covers every route work is picked up through and
every abnormal ending, including a session that died mid-work — which is a normal
ending here and the case a happy-path `plan_done` in each brief could never cover.
The live units on this fleet come from nix-fleet's `home/rich-workstation.nix`, so
the flag reaches a host only once that config carries it too.

`qb-next` already retires a finished row it walks past while claiming, on the same
per-kind rule; it needs an agent to be there, and the residue is precisely what
escapes it. A guard now holds `APPLY_STATE` against its `TERMINAL["pr"]`, because
two tools that retire a plan item on the same fact must not disagree about what the
fact is — GitHub reports an unmerged PR as `CLOSED`.
