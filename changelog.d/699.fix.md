# a dial an agent sets arrives as the value it was given

`dial_set`'s `value` was annotated `object`, which produces a schema entry carrying no `type` at all — and a parameter whose schema declares no type is one a caller may hand over as text. So `dial_set("review_panel.budget.tokens_per_pr", 8000000)` reached the board as the string `"8000000"`, and `dial_set("reviewers.sonarqube.enabled", false)` as `"false"`.

Every layer then did exactly what it promises. `POST /dials` stores opaque JSON on purpose and took them; `dials` reported them as in force; `harness_rules.board_dials` refused all three on read — *"must be a number, not '8000000'"* — and ran the repo on its own defaults instead. The refusal is printed at panel time, into a run nobody is watching, hours after the write, so the person who set the dial is the one who never finds out. On lexray on 2026-09-02 that was three of four dials, inert for as long as the rows stood.

`"false"` is the one with teeth: it is a non-empty string, so a reader that has not been told the vocabulary takes it for ON. A seat somebody switched off goes on being dispatched every round, with the board showing it as off.

The parameter now names every JSON type, so a caller that honours the schema sends a number as a number. Beside it, a value that still arrives as text is read as the value it looks like — JSON where it parses, the string where it does not, which is `qbdata.parse_dial_value`'s rule and `dials.html`'s. `P2`, `eager` and `sonnet` do not parse, so the values that always worked are untouched; the reply carries `value_read_as` when a string was read, because a silent coercion is the same class of problem as a silent refusal.

It is not that rule to the letter, and the two departures are decided rather than inherited: both of the others read a text box and strip it, where this reads an API parameter and leaves a caller's whitespace alone, and `NaN`/`Infinity` stay text here as they do in the browser — `qbdata` reads them as floats the board then refuses, which is #703 rather than a rule worth copying.

Not fixed here: the board still cannot tell a caller that a stored value is one no harness will apply, and `dials` still reports a refused row as in force. Both need the harness's dial table at a layer that deliberately does not have it.
