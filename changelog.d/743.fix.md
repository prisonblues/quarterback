# an unreachable board read as permission to delete a worktree

`remove-worktree` asks `worktree-holder` who is in a tree before it destroys the tree, its
docker stack, its database and its local branch. The helper has three answers and the
teardown acted on one of them: exit 3 ("held by a named live agent") stopped it, while exit 4
("could not tell — no board configured or reachable, no curl/jq") and a missing helper both
fell through to "proceed". A board that was down therefore read as an all-clear.

That was deliberate, and for a person at a terminal it is right: somebody typed the command,
knows which tree it names, and is watching it go. It stopped being right on 2026-09-04, when
zeus began running `stack-reaper` hourly and unattended after losing its graphical session
twice to leaked per-worktree docker stacks. Nobody is watching the reaper.

So the fail-open default stays and the strict contract is opt-in. `--require-lock` — or
`QB_UNATTENDED=1`, for a caller that is a systemd unit rather than a command line — turns
"could not tell" into a refusal, and leaves the other two answers exactly as they were: a
named holder still refuses, and a board saying "nobody is here" still proceeds. A strict mode
that also refused the ordinary case would be the reaper switched off, quietly.

### The backup was not a safety net either

It is what would have to catch a loss, and it had three holes that compounded.

`git status --porcelain` with no `--ignored` cannot see ignored files, which in a real
worktree are `.env`, `data/`, `CLAUDE.local.md`, `.worktree-port` and `.claude/` — the half
that exists in no other copy. What the backup *did* archive was tracked-and-modified files,
every one of which is either committed elsewhere or trivially remade. It is `--ignored` now.

The failure branch was `|| echo "Backup failed"` with no `exit`, so the recursive delete four
lines later ran anyway: the one run where the backup matters was the run where it was
skipped. A failed backup now aborts the teardown before anything is destroyed, and
`--no-backup` is the way past it for a tree whose contents cannot be archived at all —
without an escape hatch the guard would make such a worktree permanently un-removable, and a
guard like that gets deleted rather than obeyed.

`--ignored` brings a problem with it, so the collection drops the well-known build
caches and vendored dependency trees — `.venv`, `node_modules`, `__pycache__`, `.pytest_cache`
and their kind — where git reports them as ignored. The equivalent sweep in `stack-reaper` put
11 MB of `.pyc` into an archive meant to hold a few KB of config on its first real run; where
one of those is a real directory rather than a symlink it is hundreds of megabytes, gzipped on
every teardown. Ignored files that are not caches still go in, and a *tracked* file that
happens to sit under one of those names goes in like any other.

The porcelain parsing used `substr($0, 4)`, which handles a space and nothing else. git
quotes and C-escapes any path holding a quote, a newline or a non-ASCII byte, so `café.txt`
reached `tar` as the eleven literal characters `caf\303\251.txt` and was silently dropped.
The list is `-z` NUL-delimited end to end now, which also means a rename's second record is
consumed rather than mis-read as a status line, and deletions are dropped from it — `tar -T`
fails the whole archive on one entry it cannot stat, and a `git rm` in a doomed worktree is
ordinary.

### Still not a lock

Between the check answering and the `rm -rf` landing, an agent can still be handed the tree.
Closing that needs a real claim taken by the teardown and held by every session working in a
worktree — `flock` under `$XDG_RUNTIME_DIR`, acquired by `create-worktree`, released on
`/drop-worktree` or by its own TTL. That half of #743 is not here. What is here is the part
that turns the race into a recoverable loss instead of a silent one, and the opt-in that lets
the unattended caller refuse to guess.

### And now the lock itself

The half above turned a race into a recoverable loss and let an unattended caller refuse to
guess. It did not stop the race. `worktree-holder` is a read, and a read is worth only what
it is still worth when the caller acts on it — and between `remove-worktree` asking and its
delete landing there is a `gh` call that allows itself twenty seconds, a `docker compose
down` and an nginx restart.

`worktree-lock` is the latch: a `flock` over a lockfile keyed to the worktree's path, under
`$XDG_RUNTIME_DIR/quarterback/worktree/` — or `$TMPDIR/quarterback-<uid>/worktree/` for a
systemd timer, which has no runtime directory. `remove-worktree` takes it before it reads
anything and holds it until it exits; `create-worktree` takes it before its "already exists"
refusal and holds it for the whole checkout; and `worktree-lock --enter` takes it to write
the session marker that makes an agent visible to `worktree-holder` at all. `/fix-issue`
writes its marker through that one command now, instead of a `printf` into the cache
directory.

Two teardowns of one worktree can no longer interleave — the second waits and then aborts,
having destroyed nothing, and names the process holding it. An agent can no longer be handed
a tree mid-teardown, because the handover and the teardown take the same lock: either the
marker lands first and the teardown sees a holder and refuses, or the teardown holds the lock
and the handover waits, then finds no tree and says so. And a teardown and a creation of the
same name can no longer overlap, which used to end with a fresh worktree's database dropped
and its branch deleted by the teardown finishing underneath it — a defect the issue never
named, because it is the same race read from the other end.

`remove-worktree` also asks `worktree-holder` **twice** now: once up front, where a refusal
costs nothing, and once immediately before the directory goes. The lock means the second can
only ever differ for one reason — an agent that entered with no session marker, which is a
person typing `cd` and the one route into a worktree that nothing intercepts. That route is
narrowed rather than closed, and the late refusal says out loud that the stack is already
down and the nginx block already gone, because an abort there is not free.

**There is no TTL, and that is the answer rather than an omission.** The issue asked for one
so that a killed session frees its tree with nobody intervening. `flock` already does that,
and better: the lock lives on an open file descriptor, so the kernel drops it the instant the
holder dies — a kill, an OOM, a power cut — with no reaper, no clock and no window in which a
dead holder still owns a tree. A TTL would keep that lock for the rest of its term, which is
precisely the state the requirement exists to prevent. For the same reason the lockfiles are
never unlinked: removing a file while holding a `flock` on it is how two processes come to
hold the same lock.

**It is machine-local, and it is not a board claim.** A worktree can only be rewritten from
the machine holding it, which is the same reasoning that makes `worktree-holder`'s markers
machine-local, and the case that bites today is zeus's own hourly reaper racing zeus's own
agents. The board's claim could not carry this in any case: it is keyed on an *issue*, so a
worktree whose branch names no issue has nothing to take, and `worktree_of()` on a claim is
what was written down at checkout rather than a statement that the tree is still there.

**The interactive default is untouched.** No `flock`, no writable runtime directory, no
`worktree-lock` installed: the teardown says so and proceeds. `--require-lock` — the flag
that has been named for a lock since the half above shipped it against the holder check
alone — is what turns that into a refusal. The one new refusal an interactive caller can meet
is a lock genuinely held by another `create-worktree` or `remove-worktree` on that same tree,
and `--force` does not lift it: force has always meant "I have looked and the agent is done",
never "run two recursive deletes over one directory at once".

### Two corrections the first cut of the lock needed

**The lockfile lives in the repository, not in the caller's environment.** The first cut
chose the lock directory from `$XDG_RUNTIME_DIR` when it was set and `$TMPDIR` when it was
not — a property of *who is calling* rather than of the tree being locked. An interactive
agent has a runtime directory; a systemd unit does not, and `PrivateTmp=yes` gives one its
own `/tmp` besides. So the hourly reaper and the agent it was racing computed the same key,
the same digest, and locked two different files: the mechanism was inert for exactly the
pairing this issue is about, and every test passed, because a test harness hands both sides
of a test one environment. It is the repository's own common git directory now —
`<repo>/.git/quarterback/worktree/` — which is one answer per repository, the same from a
linked worktree as from the main checkout, and nothing an environment can move. If it
cannot be resolved there is no lock at all, rather than a second place to put one. The
regression test runs the two sides with deliberately different environments, which is the
only shape of test that could have caught it.

**No git child may outlive its holder still holding the lock.** A descriptor is inherited
across fork and exec, and git runs auto-maintenance detached: `git maintenance run --auto
--detach` follows `fetch`, `merge`, `pull`, `commit`, `rebase` and `am`, and daemonises
before deciding whether it has any work. Such a child inherits the lock and keeps it for
the length of a repack, long after the script that took it has exited — after which the
next teardown refuses, naming a pid that is already dead. The first cut closed the
descriptor for `git fetch` and asserted the rest were synchronous; `create-worktree`'s
`git merge --ff-only` was not. The rule is set once now, where the lock is taken:
`gc.auto=0` and `maintenance.auto=false` through `GIT_CONFIG_*`, which every git the holder
runs inherits, including the ones nobody has written yet.

Three smaller things came with them. `--ignore-lock` on both scripts is the way past a lock
that nothing will release, for the same reason `--no-backup` exists — a guard with no
escape hatch gets deleted rather than obeyed — and the refusal now says whether the process
recorded in the lockfile is still alive, because pointing somebody at a pid that exited an
hour ago is worse than saying nothing. `flock` is treated as a runtime dependency: the
package wraps `create-worktree` and `remove-worktree` with util-linux on `PATH`, because a
systemd *system* unit's stock `PATH` has neither util-linux nor NixOS's
`/run/current-system/sw/bin`, and a reaper that silently found no `flock` would refuse every
hour under `QB_UNATTENDED=1` and quietly rebuild the pile of orphaned stacks it exists to
clear. And a worktree spelled `<tree>/.`, `<tree>/..` or `<tree>//` now keys the same
lockfile as `<tree>`: `--enter` is a CLI a slash command drives, so its argument is prose.

A filesystem that cannot lock at all is also handled now rather than mistaken for a busy
one. `flock` spends exit 1 on both "somebody else has it" (silent) and "this filesystem
cannot do that" (which says so on stderr), and reading the second as the first would have
wedged every worktree on an NFS mount without lockd, with `--ignore-lock` the only way to
touch any of them. The stderr is the discriminator, and the second answer is a
"could not lock here" — the same one a missing `flock` gets.

One claim in the first cut was too strong, and it is corrected rather than defended. The
lock guarantees the *order* of a handover and a teardown; it cannot make the board answer.
With the board unreachable `worktree-holder` says "could not tell", the interactive default
proceeds on that by design, and a correctly marked agent can still lose its tree. That is
what `--require-lock` is for, and the comments say so now.
