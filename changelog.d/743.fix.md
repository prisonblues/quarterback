# an unreachable board read as permission to delete a worktree

`remove-worktree` asks `worktree-holder` who is in a tree before it destroys the tree, its
docker stack, its database and its local branch. The helper has three answers and the
teardown acted on one of them: exit 3 ("held by a named live agent") stopped it, while exit 4
("could not tell — no board configured or reachable, no curl/jq") and a missing helper both
fell through to "proceed". A board that was down therefore read as an all-clear.

That was deliberate, and for a person at a terminal it is right: somebody typed the command,
knows which tree it names, and is watching it go. It stopped being right on 2026-09-04, when
zeus began running `stack-reaper` hourly and unattended after losing its graphical session
twice to leaked per-worktree docker stacks. Nobody is watching the reaper.

So the fail-open default stays and the strict contract is opt-in. `--require-lock` — or
`QB_UNATTENDED=1`, for a caller that is a systemd unit rather than a command line — turns
"could not tell" into a refusal, and leaves the other two answers exactly as they were: a
named holder still refuses, and a board saying "nobody is here" still proceeds. A strict mode
that also refused the ordinary case would be the reaper switched off, quietly.

### The backup was not a safety net either

It is what would have to catch a loss, and it had three holes that compounded.

`git status --porcelain` with no `--ignored` cannot see ignored files, which in a real
worktree are `.env`, `data/`, `CLAUDE.local.md`, `.worktree-port` and `.claude/` — the half
that exists in no other copy. What the backup *did* archive was tracked-and-modified files,
every one of which is either committed elsewhere or trivially remade. It is `--ignored` now.

The failure branch was `|| echo "Backup failed"` with no `exit`, so the recursive delete four
lines later ran anyway: the one run where the backup matters was the run where it was
skipped. A failed backup now aborts the teardown before anything is destroyed, and
`--no-backup` is the way past it for a tree whose contents cannot be archived at all —
without an escape hatch the guard would make such a worktree permanently un-removable, and a
guard like that gets deleted rather than obeyed.

`--ignored` brings a problem with it, so the collection drops the well-known build
caches and vendored dependency trees — `.venv`, `node_modules`, `__pycache__`, `.pytest_cache`
and their kind — where git reports them as ignored. The equivalent sweep in `stack-reaper` put
11 MB of `.pyc` into an archive meant to hold a few KB of config on its first real run; where
one of those is a real directory rather than a symlink it is hundreds of megabytes, gzipped on
every teardown. Ignored files that are not caches still go in, and a *tracked* file that
happens to sit under one of those names goes in like any other.

The porcelain parsing used `substr($0, 4)`, which handles a space and nothing else. git
quotes and C-escapes any path holding a quote, a newline or a non-ASCII byte, so `café.txt`
reached `tar` as the eleven literal characters `caf\303\251.txt` and was silently dropped.
The list is `-z` NUL-delimited end to end now, which also means a rename's second record is
consumed rather than mis-read as a status line, and deletions are dropped from it — `tar -T`
fails the whole archive on one entry it cannot stat, and a `git rm` in a doomed worktree is
ordinary.

### Still not a lock

Between the check answering and the `rm -rf` landing, an agent can still be handed the tree.
Closing that needs a real claim taken by the teardown and held by every session working in a
worktree — `flock` under `$XDG_RUNTIME_DIR`, acquired by `create-worktree`, released on
`/drop-worktree` or by its own TTL. That half of #743 is not here. What is here is the part
that turns the race into a recoverable loss instead of a silent one, and the opt-in that lets
the unattended caller refuse to guess.
