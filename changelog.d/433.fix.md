# the issue list stops moving rows out from under the pointer

The ISSUES panel sorts free issues above held ones, which needs the claims — and the
claims and the issues arrive from two workers with nothing sequencing them. `self.held`
was `{}` both before the board answered and when the board said nothing was held, so the
panel could not tell "not asked yet" from an answer. When `gh` won the race it painted
every issue as free and re-sorted the moment the claims landed:

```
first paint : ['#427', '#426', '#422']
after board : ['#426', '#422', '#427']
```

A reader who picked the top row in that window clicked #427 and took #426. The
confirmation names the command, so it was never silent — but `ClickTable` exists because
"a single click acts on the row under the pointer" was worth a test, and this was the
panel breaking that on its own.

`held` is now `None` until the board answers, and ISSUES paints nothing until then. An
order the panel is about to rearrange is worth less than no order at all, and the wait is
bounded by a board call already faster than the `gh` call the rows came from — `fetch_board`
returns a state rather than raising, so a board that is *down* still releases the paint
instead of hanging it. `render_board` renders on that first answer as well as on a holder
change, because with nothing claimed the transition is `{}` → `{}` and a holder comparison
cannot see it.

The renewal guard beside it was never at fault and is unchanged: it was written for a claim
whose expiry moves on every poll, and it still is.

This is what had been making
`test_the_hammer_starts_a_fix_and_the_rest_of_the_issue_row_opens` intermittently red. It
was read as flake; it was the dashboard.
