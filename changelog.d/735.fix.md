# a sweep that could not reach the board stops reporting a clean board

`prune-worktrees` had two ways to describe a category and needed three. The claim sweep asked
`qb-claimed` for what this machine holds, and ended the ask in `|| true` with stderr dropped:

```bash
CLAIMS_JSON=$("$CLAIM_BIN" --repo-path "$MAIN_REPO" --session '' --json 2>/dev/null || true)
```

An unreachable board, a timeout, a rotated token and a payload `jq` declined all produced the
same empty `CLAIMS_JSON` as a board answering "nothing held" — and the report prints `none` for
an empty list. Two consecutive `/tree-shake` runs, nothing changed in between:

```
prune-worktrees            ->  Orphan board claims (7): #723 #722 #721 #724 #717 #716 #718
prune-worktrees --prune    ->  ✓ Orphan board claims: none        # applied nothing, exit 0
prune-worktrees            ->  Orphan board claims (7): ...same seven...
```

The middle run had been read as a sweep that ran and found nothing. The seven claims were still
live afterwards.

It matters more here than in the other five categories because only this one is on a clock.
Everything else is recoverable by sweeping again — a leftover directory is still there next
time — but a claim sits on an 8h TTL and this sweep is what exists to hand it back early
(#337), so a false `none` means the claim runs quietly to its fuse: #135's complaint arriving
through the tool built to prevent it.

### four states per category, not three

`qb-claimed`'s exit status already separated the two answers — `0` held, `1` free, `2` unknown,
documented in that file as "2 is not 1, and that is the whole design" — so the sweep now reads
it, along with an empty stdout and a payload that will not parse, and reports what it got:

```
? Orphan board claims: NOT CHECKED — `qb-claimed` exited 2 (no board configured,
                                     or it could not be reached)
```

Stderr is still dropped. The original bargain holds — an unconfigured board is a normal state
for this tool and one warning per run about a feature nobody enabled is noise — and this is the
same single line the category always printed, so nothing grew louder; it stopped being wrong.

Three things follow:

- **The database scan carries the same state.** Both paths where it was told there is a
  Postgres and could not reach one — no DB user, no container answering as that user — ended
  with an empty list and a green `Orphan databases: none`, which is the failure the README's
  own caveat records — a misresolved Postgres container reporting none over a hundred orphans in
  the real one. The loud warning stays for the candidate list; the report line no longer
  contradicts it.
- **`--prune` says outright that it swept no claims**, rather than saying nothing. Every other
  line in the apply pass reports an action, so silence read as claims handed back.
- **`Nothing to prune. Clean.` is withheld** from a run that could not look at every category,
  and names the ones it could not. That sentence is what a caller quotes back.

### the same discarded status, in five more places

The `|| true` was the reported instance and the mechanism was general: a producer piped
straight into a `while read` loop, or into a process substitution, hands the shell no exit
status, so "the command failed" and "the command found nothing" arrive identically. Every
external read in the file now captures its status before parsing what it produced.

- **The live worktree list**, which is not a category but the input every category derives
  "is this live?" from. `LIVE_LIST_OK` was set from inside the loop, so it only ever proved
  that *one line arrived* — a listing that emitted the main checkout and then failed
  satisfied it, and every other live worktree then looked like debris to a sweep whose
  `--remove-dirs` runs `rm -rf`.
- **`docker ps -a`** against a daemon that is not up: `docker` being on `PATH` is not a
  daemon answering it, and the refusal read as a host with no containers.
- **The port file**, which `[[ -f ]]` proves exists and not that it can be opened. Both
  arrays stayed empty, and `--prune` rewrites `.worktree-ports` from the empty one —
  discarding every live allocation in it.
- **The nginx config**, where `grep` has three answers and only two agree: 1 is "no worktree
  blocks in here", the ordinary state of a config nobody has wired, and 2-or-more is "I could
  not read it". Both arrived as no lines, and `--remove-nginx` would then rewrite the file it
  had just failed to read.
- **A config file that does not parse**, reaching the same place from the other side: `cfg`
  drops `jq`'s error and falls back to its default, so one stray comma erases the database
  engine, the nginx path, the worker prefix and the protect patterns. Refused at load now,
  rather than degrading each category into a "none" about nothing.

`--remove-nginx` also stops reporting work it did not do: its `awk … && mv` chain was
followed by an unconditional "removed nginx block", so under no `-e` a rewrite that never
happened still reported as one — and nginx was restarted to pick up a config nothing had
changed.

What is deliberately *not* unknown is a category that does not apply: a project naming no
database engine, and a host with neither `qb-claimed` nor `qb-release` on it, are told
something rather than prevented from looking. One half of that pair present and the other
missing is the opposite — a partial install is precisely where a false `none` hides, because
the half that is there says claims are being taken.

`/tree-shake` reads the report rather than an exit code, so it learns the same rule: a
`NOT CHECKED` line is unresolved, not empty, and the sweep is not complete.

This is `qb-doctor`'s verdicts in the sweep, and it closes the first of the three #204 symptoms
that section names — a check that could not run being reported as a check that passed.
