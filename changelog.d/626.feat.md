# the number the convergence epic is judged on stops being unreported

#631 taught a review round to say, in one boolean, whether it was a **clean
finish** — a stop that was not a cap, not a veto, and not a policy stop with real
findings left behind. `round_stop` computes `converged` from `confident`, in one
expression, so the two cannot drift apart. It then published it in the round's
JSON payload and nowhere else.

`qb record-review` has been POSTing it ever since. `ReviewIn` is declared
`populate_by_name=True` with no `extra=`, so pydantic's default `extra="ignore"`
applied and ingest dropped it — the same silent drop this file's own v2.26 note
records for `head_sha`, `unread_files` and the provenance pair, in the same file,
for the same reason. The field the whole convergence epic is judged on existed on
every round the panel had run and was recoverable from none of them.

### `converged` is a column, and that is a decision

The board already stores `stopped`, `stop_confident` and a confirmed count, and
the tempting move is to derive convergence from those. It does not work, and the
counter-example is not an edge case: a **below-floor policy stop** (#165) is
`stopped`, `stop_confident` **and** `converged: false`. The cycle ended
legitimately with real findings outstanding that the repo's own policy says are
reported and not fixed here. Every field a derivation could reach says clean
finish; the panel says it is not one.

The rest of the conjuncts are cut at `round_trigger_floor` and `cleared_floor`,
which are repo dials this board holds as opaque JSON and does not interpret. A
board-side derivation would therefore be a second implementation of a policy the
board cannot read, free to disagree with the panel about the same round — and the
direction it would drift in is the flattering one, because every input it cannot
see reads as "nothing outstanding". So what ships is the panel's own answer,
stored: migration `m6bc45ff1`, nullable, no backfill, with a CHECK that a clean
finish cannot be claimed by a round whose own stop record refuses it.

Nullable and unbackfilled because the third state is the honest one. NULL is "the
panel did not say", which is every round recorded before this — #631's own
included. Guessing `true` from `stopped AND stop_confident AND no findings`
certifies exactly the below-floor stops that are the counter-example; guessing
`false` marks cycles that did converge as failures. Neither, and
`GET /review/convergence` reports them under `unmeasured`, outside both sides of
the ratio.

### `GET /review/convergence`

The share of review **cycles** — one `(repo, pr, cycle)`, ending taken from its
terminal round — that ended in a confident dry round, split by repo, by PR size,
by PR kind read off the title's conventional-commit prefix, by the two together,
and by how many rounds the cycle took.

Three properties hold the number up:

* **Per cycle, not per round.** Counting rounds weights a repo's convergence by
  how long its loops take, which is heaviest on exactly the pull requests
  convergence is the question about. A four-round cycle that converges is one
  converged cycle, and `by_rounds` says it converged at round 4.
* **The undecided population is published, not netted out.** `open` (the terminal
  round said go again — still running, or abandoned, and nothing on this board
  can tell those apart) and `unmeasured` sit beside the rate and not in its
  denominator. Putting them in would report every in-flight cycle as a failure
  while it is in flight.
* **`rate` is null when nothing was decided, never 0.0.** A window with no
  decided cycles has no convergence rate, and 0.0 is the claim "this repo
  converges never" — which is what every pre-#626 window would have published.

`marginal_by_round` keeps this issue's original question intact at the round
grain: for round N, how many rounds ran, how many findings they raised that no
earlier round had, and how many cycles ended there having converged. It carries
its own coverage marker, because `new_findings` is nullable and a sum read
against the round count is low by however many rounds said nothing.

`converged` also rides on `GET /reviews`, `GET /review/{id}` and both grains of
`GET /review/findings`, and the `/panel` page grows one tile — dropped whole
rather than rendered as 0% when the window has nothing decided.

**What this does not change.** `app/review_queue.py` still gates `ready`/`land`
on `stopped` + `stop_confident` + nothing outstanding, which is strictly looser,
and it stays looser deliberately. A below-floor policy stop is a landable pull
request and an unconverged cycle at once; "may this land" and "did the loop
finish cleanly" are different questions, and collapsing them would either block
landings a repo's own policy allows or count them as clean finishes they are not.
