# the stash guard no longer refuses the push and then walks you into the pop

Every worktree of a repository shares one `refs/stash` — it lives in the common git dir, not the
per-worktree one — so `stash@{0}` resolves to whatever the last pusher meant, from any worktree of
the repo. The guard installed for that refuses writes to the shared ref and cannot refuse a read:
a pop deletes its entry through the reflog, which raises no ref transaction while another entry
remains underneath. The protection was therefore to keep the stack empty, and installing the guard
drains nothing, so on a repository carrying entries pushed before it the refusal was itself what
produced a pop. An agent whose plan was push, work, pop hits `REFUSED` and pops next; so does one
trying to undo a stash it believes happened. Four in a row did exactly that.

Where the entry's files do not clash with the agent's own the apply succeeds silently and drops it,
and a sibling's uncommitted work is then in a tree that never asked for it — where the blanket
`git add -A` the loop drivers run commits it under the wrong author. That is the failure the
original guard was written to prevent, arriving through the half of the verb it could not reach.

The reason for leaving `git stash` out of the pre-tool guard was sound about the push and was
written down as though it covered the verb, which is how the pop came to be guarded by nothing.
`pop`, `apply` and `branch` are now a third harm class beside destroying and absorbing a peer's
work — `takes` — and they are gated on their own two facts rather than the tree guard's three,
because a pop takes a sibling's entry with your tree clean and nobody else live in it. Those two
are that the repository has linked worktrees and that the shared stack is not empty; when either is
false a pop is nobody else's business and runs. `push` stays with the git hook, which catches it
outside Claude Code entirely, and `list`, `show`, `drop` and `clear` stay unguarded — the first two
are reads, and the last two are the only route out of a stack that already has entries on it.

One hazard, one escape hatch. `QB_ALLOW_SHARED_STASH=1` is the name the git hook already honoured
and it is what the pre-tool guard reads, so this is one gate enforced in two places rather than two
gates with two hatches — which was the standing objection to guarding stash here at all.
`QB_ALLOW_SHARED_TREE=1` deliberately does not open it: settling the shared-tree question with a
peer says nothing about whose work is sitting at `stash@{0}`.

The git hook's refusal also says, in words, not to pop — nothing of yours reached the stack, so a
pop can only hand you somebody else's entry and drop it from under them. That sentence is the whole
of the protection for a stash typed outside Claude Code, where no pre-tool hook exists.
