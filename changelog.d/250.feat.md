# the dashboard's one click that left the terminal now has a button that doesn't

Clicking a PR or an issue on `qb-dash-tui` opened a browser — `open_pr` and `open_issue` both
went to `xdg-open`. That was the only action on the dashboard that left the terminal, and it
left it to show something a terminal renders well: `gh-dash` has a full detail view for both,
Overview / Activity / Commits / Checks / Files Changed for a PR and body plus comments for an
issue. So the reason to click a row on a dashboard sitting beside your seats — to stay where
you are — was the one thing the click could not do.

WORK rows now carry a `▥` beside the `⚒` and the `⚖`, and `v` from the keyboard. It opens that
row's `gh-dash` detail view in a pane of the seat row, through the same `run_in_pane` a panel
review already uses, on the same argument: a thing you switch windows for is a thing you go and
look at later. The row click and `o` are untouched — GitHub still reaches what a terminal
cannot render, and both are already in a reader's fingers.

### `gh-dash` cannot be told to open item N, so the config is the handle

Its entire CLI on 4.24.1 is `--config`, `--debug` and `--cpuprofile`. The `▥` writes a
throwaway config whose one section is narrow enough that the item is its only row, with
`preview.open: true` so the sidebar is already there, into `$XDG_RUNTIME_DIR/qb-dash/` and
named for the item so a second click rewrites one file rather than leaving a directory of them.

The pin is the head branch for a PR and the exact title for an issue. The number — which is
what every caller already has — is the one thing that cannot be used: GitHub search has no
`number:` qualifier and a bare `is:issue 827` matches nothing. `head:<headRefName>` is exact
and costs nothing, since `fetch_prs` already asks for that field; `in:title "<title>"` holds up
on this repo's titles with their colons, backticks, apostrophes and em-dashes, because a quoted
phrase is matched over tokens. A PR with no `gh` row of its own — a plan item whose ref is a
`pr` has none, because `work_rows` attaches one only for a PR the review queue named — is
looked up in the open-PR list on the same screen before anything else, and only then falls
back to a title that is the PR's own. A plan item's own wording is never used for it: the pin
would match nothing, and an empty `gh-dash` reads exactly like a fetch that failed.

Unlike the `⚒` and the `⚖` it works across repos — those refuse a row this checkout is not,
because `/fix-issue` and `/panel-review-pr` resolve the repository from where they run, and the
generated filter carries `repo:` explicitly. And it asks no confirmation: that dialog exists
because a panel round spends money and pushes a commit, and a read-only click that asks first
is a click you learn to double-tap.

On a machine with no `gh-dash` the column greys and the click says so rather than explaining
the row — a missing binary is a fact nothing else on this dashboard reports. `PATH` is asked on
every render, so installing one while the dashboard is up lights the column on the next tick.
