# a qb-bump you prepared but never applied refused the lock you already applied

`qb-bump --apply` writes the prepared `flake.lock` into the consuming flake and leaves it
uncommitted on purpose, so it has to recognise its own handwriting on the next run or every
successful bump wedges the one after it. It recognised only the last lock it *wrote* — not
the one it read and built its proposal on top of — and a proposal that is prepared and then
left alone overwrites the first with the second.

That is the ordinary sequence, not a corner. Apply a bump; `main` moves; run `qb-bump` again
to see what the next one would do; get pulled onto something else. The working tree still
holds the lock the tool applied, untouched, and the cache now files that lock under
`base_lock_sha` rather than `new_lock_sha`. The next run refused it:

```
qb-bump: /home/rich/source/nix-fleet/flake.lock has uncommitted changes that this did not
         write. It prepares against HEAD, so applying the result would discard them —
         commit or revert that file first
```

It did write it, and the cache in front of it said so. Preparing is the cheap, safe half
people run without applying, so any such run disarmed the recognition for the lock that *was*
applied — putting the tool back in the state it was taught out of.

### Both hashes count, and the one stale case is guarded

A working tree matching either recorded hash is now prepared over. Matching the base hash
means byte-identical to what this tool read, so nothing has changed since it looked and there
is nothing of anybody's to discard — and the base is only ever recorded after the same check
has already passed that lock, so it is never a hash of somebody's in-flight work.

The exception is real and is refused rather than assumed away: if the consumer commits a
*different* lock afterwards and the working tree is left on the older content, that is a
deliberate revert, and preparing against the new HEAD would write over exactly what it was
protecting. The committed lock at the proposal's base commit is compared against HEAD's. A
consumer committing anything *else* is not that, and no longer refuses either.

### It stops claiming an authorship its own cache can disprove

The refusal now says it *does not recognise* the changes rather than that it *did not write*
them — the tool compares against two recorded hashes, so recognition is the honest claim, and
the old wording is why the report took a cache dump to disbelieve. With an empty cache it says
there is no prepared bump to account for the file, instead of implying a comparison it never
made.
