# the escalations row can see the board now, instead of reporting that it cannot

`qb-doctor`'s `escalations` row shipped in #530 unable to read a single post. It asked
`GET /board?type=stuck` through a helper that requires a JSON object, and that endpoint
answers a bare array — the `{"posts": [...], "cursor": N}` object it was written against
is assembled by the MCP `board_read` wrapper on the way out, so it is the shape an agent
sees and not the shape the API has. Every host got `unknown`, always, in a sentence
("the board did not answer an object") that pointed at the `board` and `token` rows,
both of which were `ok` and neither of which was the fault. The `/blockers` half of the
pair had never executed at all.

It reads a list now, so the row reaches a verdict: on the fleet's own board, `1 blocker
row(s) recorded against 10 stuck post(s) in the last 24h`.

Its five tests passed throughout, because the stub answered an object too — the fixture
agreed with the bug. That is the same failure #523 exists to catch, which is a signal
that looks like it is watching something and is not, so the stub is now held to the
endpoint's declared return type by a test that reads it off the source.
