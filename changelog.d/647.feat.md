# the working behind a stored count now sits on the same row as the count

`provenance_counts` has been stored since v2.26 and rides every view. Four of the
twenty-five keys #643's drift test listed as dropped-on-purpose were the working
behind it, and nothing on the row said which — so a consumer holding `introduced`
counts across a cycle's rounds was holding numbers whose denominator could have
changed underneath it, with no way to tell.

Five keys came off that list. All five are stored now.

- **`rules`** (#305) — which LAYER supplied each dial: `defaults`, `sample`,
  `overlay` or `board`, with the source and, for a board dial, the reason somebody
  gave, who set it, its scope and when it lapses. This is the only field on the
  row that records `escalate_on.fix_injection`: `review_panel`, which #643 stored,
  is `panel_seats.Dials.as_dict()` — twelve settings — and `escalate_on` is not
  among them. `rules.dials` covers every dotted path under `review_panel.` and
  `reviewers.`, fifty-two of them on this repository.
- **`provenance_restored`** (#559) — how much of the fix range the round declined
  to attribute because the cycle had already seen it, which earlier rounds it
  compared against, and `why` where the comparison could not be made at all. This
  is the filter that MOVES `introduced`.
- **`fix_range_source`** (#512) — which range answered: `increment` (the diff the
  round reviewed), `compare` (the separate API fetch used under `pr` scope and
  wherever the increment fell back) or `reconstructed` (#504's rebuild after a
  rewritten history). The three are not one measurement — the increment drops a
  base-branch merge's files and the compare range does not.
- **`scope`** and **`since_sha`** — what the round actually reviewed. `diff_chars`
  is stored and is scope-dependent, so a consumer comparing it across a cycle's
  rounds without these is comparing a whole PR against a commit range. Not
  inferable from the round number: the panel falls back to `pr` whenever the
  anchor is missing or the fetch failed.

The changelog for #642 states the trap all five close: a threshold fitted across
rounds whose `introduced` was measured against a filtered range and rounds where it
was not is a threshold fitted to a denominator that changed. #637 recalibrates
`escalate_on.fix_injection` against exactly those counts, and the round payload is
a temp file on whatever host ran the panel — a round that runs before these columns
exist has lost them permanently, on `m6bc45ff1`'s argument for `converged` and
`mc57fb9ba`'s for `review_panel`.

### Five columns, not one, and the split is deliberate

Migration `m331126c7`: `rules` and `provenance_restored` are JSONB;
`fix_range_source`, `scope` and `since_sha` are `Text`. All nullable, no server
default, no backfill, no CHECK, no index.

The scalars are not keys inside a blob because a recalibration reads a POPULATION
and slices it on them. They ride `GET /reviews` as well as `GET /review/{id}`, on
the rule `merge_base` and `base_sha` already state: a scalar whose whole point is
cross-run comparison must not cost one fetch per run. The two objects stay on the
detail view, on `review_panel`'s rule — `rules` is one record per review dial, and
a page of five hundred is a config dump.

`rules` is also **deferred**, which `review_panel` is not, on the argument
`unread_files` already lost once: keeping a column out of the JSON response still
has Postgres ship it to the app. It is the largest column on the table, so
`GET /reviews?limit=500` would fetch five hundred configuration records to
serialise none of them. `GET /review/{id}` undefers it; nothing else reads it.

And there is no object on the payload that holds all five. Composing one here would
be this board inventing a structure the panel never sent.

### Opaque, and one of them against a neighbouring precedent

The two JSONB blocks are stored verbatim and never read for meaning, on
`review_panel`'s terms. `rules` sharpens the argument: interpreting a layer would
mean this board learning the resolution ORDER as well as the vocabulary, and a
second implementation of "which file answered" is the drift #305 exists to end. A
board that read a key out of `provenance_restored` would likewise be a second
implementation of #559's filter, free to disagree with the panel about the same
round.

The three scalars are stored against no vocabulary either, and that one runs
against `pr_state` one validator over, which coerces anything outside its set to
NULL. The precedent does not carry: GitHub's states are a foreign, stable set and a
variant spelling silently reclassifies a PR in the direction that hides work.
Neither half holds here. `fix_range_source` was two values when #512 published it
and #504 added a third, so a frozen set written on this board would have dropped
`reconstructed` on the release that introduced it — this issue's own bug one layer
down. And an unrecognised value forms its own group in a consumer's `GROUP BY`
rather than being folded into one it cannot see.

What is refused is being a WORD rather than which word, and being storable rather
than being meaningful: a wrong shape, a NaN, a NUL inside a string, or an
over-length record. The objects refuse WHOLE rather than trimming — a `rules`
record with half its dials dropped cannot be told from one whose resolver never saw
them — and each refusal is named back to the sender under `rules_dropped`,
`provenance_restored_dropped`, `since_sha_dropped` or `unreadable_fields`, because
a refusal in silence reads exactly like a round that had nothing to say.

`MAX_RULES_CHARS` is measured rather than picked. The record is 7,299 characters on
this repository today; `app/models/dial.py` bounds a board dial's reason at 2,000
and its path at 200, so a repository whose every review dial came from the board
with a maximal reason produces about 148,000 characters — a configuration this same
board permits somebody to create. The bound sits above it, because the refusal is
whole-object and one long argument must not cost the layer for all fifty-two dials.

### And a false refusal, carried over from #643 and fixed for both

The shared coercer these three blocks now go through caught a defect in the one
#643 wrote. Its NUL check scanned `json.dumps`' output for the six characters an
escape sequence spells, which cannot tell a real NUL from a string that merely
CONTAINS that text: the dump writes a real NUL as those six characters and writes
the literal text as seven, with the backslash doubled — and the seven contain the
six.

That is not a curiosity on `rules`. It carries board-dial reasons written by
people, and a reason quoting an escape sequence would have had the whole record
refused — fifty-two dials' provenance lost, permanently, to a NUL that was never
there. The refusal is whole-object by design, which is what makes a false positive
expensive. The check now walks the parsed value instead, which also reaches dial
PATHS; scanning the dump was only ever done because it reached keys.

`review_panel` gets the repair for free, being the same function.

### What still fails

`tests/test_payload_key_drift.py` is the mechanical half of the acceptance and it
stays green: the five keys came off `DROPPED_BY_DESIGN`, which now lists twenty,
and `test_the_provenance_working_is_bound_and_no_longer_dropped` asserts each is in
the payload, bound by `ReviewIn`, backed by a column and off the list — four
assertions, because a field with no column stores nothing and a column with no
field is the `converged` shape exactly.
