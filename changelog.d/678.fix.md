# a background poll no longer throws the reader back to the top of WORK

Scroll thirty rows down a seventy-row WORK table, and the next poll that changed anything at all put
you back at row one. `render_work` rebuilds by clearing the table and adding every row again, and
`DataTable.clear()` resets `scroll_y` — so the row you were reading, and the ⚒ you were reaching for,
went with it.

`work_sig` (#433) already limits this to the polls that changed something, on the argument that a
reader picks a row by looking at it. This is what the polls that DID change something were still
costing. The row at the top of the view is now put back at the top of the view after a rebuild,
anchored on its key rather than on the scroll offset: a rebuild can insert rows above the view — a
question nothing else draws gets a row of its own, at the top — and a restored offset would show a
different stretch of the table while claiming to have kept your place.

The cursor is deliberately not restored with it. It resets to row 0 on a rebuild today, and carrying
it across would change what `selected_work` answers after a poll, which is a separate argument.

### the same defect, wearing the costume of a dashboard bug

This is the diagnosis #678 asked for. The four live dashboard tests click whatever the board has open
at the moment they run, and `test_the_hammer_starts_a_fix_and_the_rest_of_the_issue_row_opens` failed
with `the icon did not raise the confirmation` — which reads exactly like a ⚒ that does not work.
#678 measured one failure in three runs; unmodified `main` on this box gave two in thirty, wearing
#679's clearer wording for the same event (`work never settled with a row at (3, 22)`). Both are
measurements of a board on a day rather than properties of the code, and neither rate will reproduce
— what generalises is the shape, a rebuild landing between reading a row's position and clicking it.

It was not. `refresh_board` is one worker making two board calls in a row: the claims, then the
questions a person owes. The drivers stop waiting the moment the CLAIMS land and then stub
`refresh_board` — which does nothing to the worker already inside it, so the second call arrives one
board round trip later, after `_settle_table` has pronounced the table still and after
`_click_row_index` has read the screen position of the row it wants. The rebuild sent the table back
to the top, and the click went to whatever the top put under that position — usually a row whose ⚒ is
grey by design, which raises no confirmation and says so on the detail line nobody was reading.

`_settle_table` could not have caught it. It watches row KEYS, and a question that rides a row this
table already draws rewrites that row's state, its verb and its last cell without changing a single
key.

So the drivers now wait for every in-flight worker to finish before they freeze anything, rather than
for the one answer they happen to be watching. `refresh_plan` and `refresh_prs` have the same shape —
the plan and then the dials, the PR list and then the queue — and with the blockers call closed but
the PR list still in flight the failure came back in a new costume: a ⚒ click that raised the PANEL
confirmation, for a PR that had appeared on the board a moment earlier.

### two smaller things in the same file

`test_the_hammer_starts_a_fix_and_the_rest_of_the_issue_row_opens` was the only one of the four with
no guard on the board holding something it can act on. It excluded rows a person owes an answer about
and nothing else, so it would happily pick an issue an agent had claimed, or one belonging to a repo
this dashboard only watches — both of which draw a grey ⚒ on purpose, and both of which then read as
the dashboard being broken. It now asks `work_action` whether the ⚒ is live, which is the same call
the renderer makes when it decides whether to draw the icon in cyan, and skips when nothing on the
board offers one.

And every "did not raise the confirmation" now carries the detail line with it. Each of the five
refusals on that path ends in `say`, and `say` is the pane's one visible answer to "did that click do
anything" — the bare sentence was the whole of what #678 had to go on.

### what the restore refuses to do

Deferring the restore by a refresh is forced — `clear()` marks the table's dimensions stale, and a
scroll set inline is clamped against a virtual size of nothing and reads 0 one pause later — and
deferring opens a gap. Two things can happen in it and both win over the restore. A newer rebuild
supersedes an older one, which matters because the callbacks run in the order they were queued, so
without a generation counter the OLDER rebuild's anchor lands last. And a reader who has scrolled
since is left alone: `clear()` put the view at the top, so a scroll position that is no longer the
top belongs to somebody else, and overwriting it would be this doing to them exactly what it exists
to prevent.

The viewport is restored and the selection is not. `clear()` sends the cursor to row 0 as well, and
it is left there — restoring it would drag the viewport to it, because `watch_cursor_coordinate`
scrolls the cursor into view, which is the same defect arriving from the other direction. Carrying
the cursor across a poll also changes which row a keypress acts on, and that is a behaviour change
with its own tests to write rather than a side effect of keeping the view still.

Near the end of a table that has shrunk, `scroll_to` clamps at the last screenful, so the anchor row
lands part-way down the view rather than at the top of it. That is the right answer — there is
nothing below it to scroll — and it is still the reader's row on screen.
