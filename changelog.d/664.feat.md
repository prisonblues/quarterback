# a PR can be too small to afford the smallest honest fix, and the growth ceiling now knows it

`max_fix_growth` is a multiple, so the growth a PR may absorb is `(k - 1) × first_chars`. On a
**439-character** PR at the default `3.0` that is an allowance of **878 characters**.

The minimum honest single-hunk fix measured on that PR cost **827 characters**, of which roughly
**430** is unavoidable diff framing — `diff --git`, `index`, `---`/`+++`, `@@`, and the context lines
a hunk must carry. So **49% of the entire growth allowance was framing**, one hunk in one file was
the whole affordable budget, and a second finding whose fix was ~200 characters was unaffordable
whatever else was true about it.

### the breakeven, which is the part that generalises

Framing cost is fixed per file-hunk and does not scale with the PR. The allowance does. So there is
a size below which the ceiling forbids the smallest truthful fix that exists:

| what the allowance equals | at a PR of |
| --- | ---: |
| one hunk's framing (~430 chars) | **215 chars** |
| the measured minimum honest hunk (827 chars) | **413.5 chars** |

Below ~413 characters a 3.0x ceiling cannot afford a single honest one-file fix. The dial stops
meaning "a fix pass that multiplies the diff has written a second change" and starts meaning "this
PR is too small to be fixed at all".

It did not merely refuse a fix on the cycle this came from — it wrote one. The fixer declared two
corrections it could not pay for, and the next round found one of them: a `classify()` KEEP reason
the change had made wrong. The ceiling produced a regression and then bought a round to rediscover
it.

### `min_fix_growth_chars`, at 2,000

A floor under the **multiple**: the ratio half fires only where the PR has also grown by more than
this. `max_fix_growth_chars` is untouched by it, so a PR of any size that grows past 30,000
characters stops exactly as it did.

2,000 is about a two-file fix — ~860 of framing plus ~1,140 of content, roughly 17 churned lines at
PR #188's own measured 66 characters a line. It sits far below the 30,000 absolute ceiling on
purpose: the floor guards the ratio only, so a floor near that ceiling would leave the multiple
unable to fire *first* and crossed-first would have inverted. A repo that writes one at or above the
absolute half is told so in `config_notes`. `0` is refused — a floor every growth clears is the off
position written in a spelling that does not say so — and `null` is the exact pre-#664 behaviour.

### the sentence this makes false

`max_fix_growth`'s block claimed the pair "can only ever TIGHTEN: nothing this arrangement lets
through would have been caught by the multiple alone." A floor is the first term in this mechanism
that **loosens**, so that claim is now narrowed everywhere it was written — `harness_rules`,
`panel_core`, `panel.py`, both READMEs and `.harness-rules.sample` — to the pair of ceilings it is
actually true of, rather than left to be discovered.

### what was considered and rejected

Measuring both ends **net of framing** — subtracting `diff --git`/`index`/`---`/`+++`/`@@` before
taking the ratio — measures the thing the dial claims to measure instead of approximating it, and
needs no key at all. It is rejected because `pr_chars` on every baseline already in flight is a raw
character count, so a framing-net numerator would decline to run on every cycle in flight and every
payload behind it. That is #169's ships-unwired failure, and it is the same objection #492 used to
reject a `_lines` dial.

#551 is this sizing question from the other end and this key does **not** settle it: what
`low_severity_fix_lines` wants is a *ceiling*, `min(lines, pct × the first round)`, because the
accumulation it measures is dangerous on the small PR — the same end this floor loosens. Same
question, opposite operator.
