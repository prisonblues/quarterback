# a standing blocker stops reading as a severed producer

`qb-doctor`'s `escalations` row asks whether the escalation path is writing rows or only ringing
the bell, and it had been FAIL on zeus for days against a producer that was working:

```
escalations  https://qb.fo.ls  27 stuck post(s) in the last 24h 00m and not one blocker
                               row — the escalation path is ringing the bell and recording
                               nothing, so nothing can answer 'what is waiting on me'
```

Measured against the live board on 2026-09-04:

| | |
| --- | --- |
| blocker rows total | **25** |
| rows raised inside the 24h window | **0** |
| age of the newest row | **34.5h** |
| `stuck` posts inside the window | 28 |

Every one of those posts was a re-announcement of a question that already had an open row —
`unpushed@zeus`, `landed`, `escalations`, `rebuild-waiting@…`. That is `_raise_blocker` behaving
as designed: the partial unique index on `(subject, class, condition)` makes re-raising a no-op,
so `announce()` returns `, already an open blocker` and writes no second row. A `qb-bump` run
during the investigation printed exactly that.

### the window bounded the wrong thing

The fault condition was *a post in the window and no row **raised** in the window*:

```python
fresh = [b for b in stored if 0 <= _age_minutes(b.get("raised_at")) <= window]
if raised and not fresh:
    ... "fail"
```

A standing question is announced repeatedly and stored **once**. Once its row ages past 24h,
every later announcement lands in `raised` and nothing lands in `fresh` again — so the row goes
FAIL and stays FAIL for as long as the question goes unanswered. The longer a human left a
blocker, the more confidently this row reported that blockers were not being recorded.

It was self-sustaining: two of the 25 standing rows were `environment/escalations` and
`chore/escalations`, this row escalating about itself, its own escalation now one of the rows
keeping it red.

The check had already written down the fact that breaks it, three lines below the branch it
breaks:

> Rows and no posts is not a fault either: a person can raise one by hand, and **the window is a
> day while an unanswered blocker outlives it.**

### behind, not beside

A post is now **accounted for** when an open row of any age carries its subject, matched the way
`_raise_blocker` files it — `refs` through `needs_human._SUBJECT_PREFERENCE` on one side,
`subject` on the other. The fault is a post that should have produced a row and has none.

Every case the row exists to catch survives, because in all of them there is no row to match
whatever its age: #328 deployed with no producer, `_raise_blocker` failing, a board predating the
table. What it stops catching is a fleet whose questions are simply older than a day.

Three things follow.

- **#523's exclusion moves into the denominator.** An escalation whose refs name no subject is
  announced and deliberately not stored, so those posts could never have had a row and are not
  evidence either way. Counting them would have traded one false alarm for another — a producer
  correctly declining to store noise, reported as severed. A run in which *every* post is that
  shape now says so, rather than reporting a zero as a fault.
- **A resolved row stops vouching.** An answered question is not a standing one, so posts still
  arriving after it was resolved are once again unrecorded.
- **The sanity floor stays.** Dropping the window's upper bound is the fix; a row dated in the
  future is still discarded, as clock skew or bad data that is not a fact about anything. Losing
  that would have been a quiet cost of the change rather than part of it.

The full-page guard is still `unknown` and now for a sharper reason: matching is by subject, so a
truncated oldest-first page is an incomplete subject set, and a post that looks unaccounted for
may simply have its row past the cut.

`ESCALATION_SUBJECT_PREFERENCE` is a second spelling of `needs_human._SUBJECT_PREFERENCE`, since
`qb-doctor` imports nothing from `harness/loops` — held to the original by a test that reads the
tuple out of that source, on the precedent of the `needs_human` class literals next door. A
silent divergence there would leave every post looking unaccounted for: the same false alarm
arriving by a different route.
