# two hosts recording one merge no longer write two receipts

`POST /plan/item/done` was a read-modify-write with no row lock and no condition:
every caller that found the item open stamped `done_by` over the last one and
appended its note either way. That was tolerable while the observers were people
and the agents they were driving — "whoever observes it may write it down" is the
endpoint's design, and a person adding a sentence after an agent is exactly right.

#552 put an **actor** behind it. `qb-reconcile --apply` runs on a fifteen-minute
timer on every machine in the fleet, each host reads the same open row, and
`apply_note` renders byte-identical text on all of them — no host in it, no
timestamp. So an item the fleet finished collected one receipt per machine, and
two ticks landing together could lose one another's append outright, since each
read the note a round trip before writing it back.

The transition is now a conditional `open -> done` UPDATE, the pattern `renew_claim`
already uses on the claims table and for the same stated reason: the predicate is
evaluated by the database at write time, so the row cannot move between the look
and the write. Exactly one caller transitions it. The others are answered 200 —
the row is done, which is what they wanted — with `changed: false` and `done_by`
naming who won, and their receipt is not appended a second time if the row already
carries those words.

**A second observer with something else to say is still heard.** What is refused
is the same sentence twice, not the second caller: a person's `plan_done` following
an agent's lands under it as it always did. Dropping every note on a no-op would
have bought a duplicate's removal with a silence.

"The same sentence" is matched as a whole receipt line, not as a substring — a
second-opinion review of this change caught the first cut swallowing `landed in
PR #143` because the row already read `landed in PR #143 after the schema change`.
Losing a distinct sentence is the failure the no-op path was written to avoid, so
the wider rule would have introduced it while removing the duplicate.

### The drop that could be finished over

Found while writing the test for the above, and older than it. "A human dropped
this item" is the one state `done` refuses, and the check for it read a row the
transaction had not locked — so a drop that committed in the gap was finished over,
and an agent stamped `done` on top of a person's decision. That is the human-only
rule being routed around, quietly and in the record. The conditional UPDATE closes
it: nothing transitioned means the row is re-read, and a dropped one is refused
where the write is rather than where the read was.

### `qb-reconcile` reads the answer instead of inferring one

`_already_done` compared the returned `done` stamp against the moment its own write
went out and named whoever appeared to be earlier. It carried an explicit residual:
a host whose clock ran fast named a peer for a receipt that was its own, and a slow
one stayed quiet about one that was not — with neither host able to tell which had
happened. It reads `changed` now, decided where the transition was, and the residual
is gone with the comparison it belonged to. A board older than this change returns
no `changed`, and the pass says nothing rather than guessing.
