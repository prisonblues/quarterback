# three of five hosts read "NOT wired up" for running their own design

`qb-doctor`'s `reconcile` row asked "is `qb-reconcile.timer` enabled **here**". The pass it
asks about is a fleet singleton over a plan every host shares, and `/plan/reconcile` is built
for more than one reporter — "two hosts hold this timer and their passes can land together".
Which host holds it was never the question anyone wanted answered.

In nix-fleet the units come from `home/rich-workstation.nix`, reached only via
`modules/desktop.nix`, which only the two desktops import. atlas, sisyphus and daedalus could
therefore never pass that row. One `fail` sets the headline in `summary()` and makes
`exit_code()` return 2, so on three of five machines every other row went out under a verdict
that was false — including the rows a reader would act on.

The row now splits on whether the host has the units at all. It **has** them: the old local
check, unchanged, because a timer that exists here and is dead is this host's fault and no
board can see it. It does **not**: ask the board whether anyone is reconciling. `ok` names the
machine and the age rather than saying "not my job", since an `ok` that hides what it is
trusting has only told the reader to stop worrying.

### The evidence a clean pass used to destroy

Neither existing signal could answer it, and both fail open exactly when the fleet is healthy.

`qb-reconcile --post` is gated on `has_content`, so a pass that finds nothing posts nothing at
all — "no `finding` post in four hours" is the signature of a healthy fleet as much as a
stopped one. And the `/plan/reconcile` write, which does fire every pass, sends an empty
findings list for a clean scope; the endpoint then deletes every row it did not re-report. A
healthy scope leaves `plan_reconcile` empty, which is the same table state as a board nothing
has ever reconciled.

So the board now records **that a pass ran** — scope, machine, time — beside what it found and
never folded into it, and `GET /plan/reconcile` reads it back. One row per scope: per pass
would be a log, ~96 rows a day per host, to answer a question only ever about the newest.

Reading either old signal as a heartbeat would have traded a noisy false alarm for a quiet
false pass, which is the absent-result-as-benign collapse `_edge_spoof_refused` is annotated
against — arriving in the row where it is hardest to notice, since it would have failed open
at the moment nothing else was complaining either.

### What still fails, and what only warns

Nothing anywhere having recorded a pass stays a `fail`: that is #255's original night, the
units in-repo and on no host, and it is a real fault. A fleet whose newest pass has aged past
an hour is a `warn` — "the machines that hold the timer are off" is a fact about the day, and
installing a second timer to clear the row would silence the symptom on one host while leaving
the fleet's pass exactly as stopped. A board too old to answer is `unknown` rather than `fail`,
because the endpoint ships with this change and reading a 404 as an outage would manufacture
one out of a deployment lag.
