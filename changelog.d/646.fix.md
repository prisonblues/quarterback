# a NUL or a NaN anywhere in a round payload no longer costs the whole round

Postgres will not hold a NUL inside a `text` column or a `JSONB` string, and it will not hold
`NaN`, `Infinity` or `-Infinity`. Python's `json.loads` — which is what starlette parses a
request body with — accepts all four. So a `POST /review` carrying one passed every validator
in `app/api/reviews.py`, reached the INSERT, and **500ed**.

That is the one failure a panel cycle cannot survive quietly. The panel reads an empty stdout
under exit 0 as "the board did not answer", so the round is simply not recorded and from the
panel's side it is indistinguishable from a board that was down — leaving a silent hole in the
record every stop decision and every provenance figure is computed from.

#643 fixed one field (`review_panel`), #647 fixed two more and #112 fixed `scope` in passing,
each in its own validator. A
probe against this board's own test database found the same 500 in **twenty-eight other
places**: `pr_title`, `base`, `skip_reason`, `stop_reason`, `cycle`, `session`, `run_key`,
`judge_model`, `judge_skip`, `coverage_note`, `sonar_gate`, `ci_status`,
`reviewers_override`, `scope`, `fix_range_source`, both path lists, `reviewers_selected`,
`skipped`, the stop veto, the `reviewers` mapping's own KEYS, every per-seat string, every
finding's title, detail, reason, file, severity and key, and every per-reviewer account.
Twenty-eight coercers each remembering is not a rule, so this is one pass over the whole body
in `ReviewIn`'s existing `mode="before"` model validator, which is the only place that sees
every nested value while it is still a plain mapping.

### Strip, refuse, or 422 — three answers, decided by consequence

The issue was filed because the right answer is not the same for a file path as it is for a
policy record. It still is not, and the deciding question in each case is what a wrong answer
would silently assert.

**A token matched by exact string is dropped.** `unread_files`, `changed_files[].path`, a
finding's `file`, `code_access.convention_files_removed`, and — since #112 landed —
`harness_path` and `harness_digest`. The test is not "is this a path", it is *is this compared
with `==` somewhere that will not report the miss*: the unread list against the next round's
diff to fill the `missed-unread` bucket, the changed files against another PR's in
`GET /review/collisions`, a finding's file inside `_derive_key`, a digest against the previous
round's to answer the "same code, or not" question #112 says that field is never wrong about. A
marked token is not a shorter one, it is a *different* one — it would sit in the column looking
like data and answer its comparison wrongly, silently, forever, where NULL answers *unknown*.
That is the argument `_unread_paths` already makes for dropping an over-long path rather than
truncating it, and the one #112's `_word_or_none` makes in the same words about a truncated
store path naming a directory that does not exist. Each path lands on the "this entry was not a
path" state its own field already has, so `unread_files_dropped` and `changed_files_dropped`
keep counting it and the arithmetic still closes.

**An opaque policy record is refused whole, unchanged.** `review_panel`, `rules` and
`provenance_restored` keep #643's and #647's refusal, and the new pass deliberately does not
reach inside them — so #78's `threshold_by_severity`, a mapping nested inside `review_panel`
that arrived after this pass was written, is refused with the dial set rather than edited
inside it, and nothing here had to learn the new key. Half a dial set is not a smaller policy but one no round ran under, and a
normalisation that reached in would store a policy differing by a character from the policy
that ran, on a row claiming it was intact — worse than either the 500 or the refusal.

**Everything else keeps its value with the NUL replaced by `␦`.** Prose, names, identities,
vocabulary words and mapping keys. The alternative for a reviewer's `account` or a stop's
`veto` is to store nothing, and a missing account is a worse record than a marked one. The
mark is what stops it being a silent edit: `_echo` has replaced control characters with `␦`
rather than deleting them since the drop signals were built, on the grounds that a reader
should see that something unprintable arrived — this applies that rule to values on their way
**in** to a column, which is the half the issue points out it was never applied to. It is
deliberately not `_echo`'s full C0/C1 replacement: a `detail` legitimately contains newlines,
and normalising those would rewrite text nobody objected to.

A marked value is not thereby believed **where a coercer follows it**. `head_sha`,
`harness_rev`, `provenance` and `pr_state` meet theirs straight afterwards and are refused
there, under the drop signal each already had — so a NUL'd `harness_rev` reports both the mark
and #112's `harness_rev_dropped` quoting what arrived, which are complementary rather than
competing. Where no coercer follows, the marked value is **stored**, and `scope` /
`fix_range_source` are the deliberate case.

That is where this parts company with #112, which refused them. `_word_or_none` reads those two
against no vocabulary on purpose — it says a frozen set here would have dropped `reconstructed`
on the release that introduced it — and its own conclusion is that an out-of-set value
reclassifies nothing, because a consumer grouping a population by the field gets an extra group
it can SEE rather than one folded into a group it cannot. NULL *is* that fold: it is what every
round recorded before #647 carries, so refusing the word makes a corrupted round
indistinguishable from an old one. `increment␦` is visibly not a scope and is reported, and can
be mistaken for neither.

**#112's own NUL check is removed rather than kept beside this.** It found the real 500 and
fixed it correctly for the code as it stood; the whole-body pass now runs before
`_word_or_none` is ever called, so the check could no longer fire. A dead check in one of
thirty coercers is worse than none — it reads as though that were a place NUL is handled, which
is the per-field habit this issue exists to end — and the function's docstring records what was
taken out of it, why, and that the answer is not the same one.

**Nothing is a 422.** A 422 loses the round, its findings, its scorecards and its accounts over
one byte, which is exactly the loss this issue is about. The one exception is `repo`, which
already refused a NUL because it is not in `REPO_RE`'s character class and which stays that
way: `repo` is the row's identity, every read compares it with `==`, and a marked spelling
would be a second repository nothing ever asks about.

### Reported, in three keys, because they want three different fixes

`nul_replaced`, `nul_dropped` and `nonfinite_dropped` name the **dotted positions** —
`to_fix[0].reported_by[0].account`, `reviewers.claude.model`, `unread_files[0]` — so a sender
is not left diffing its own payload. Three lists and not one, on the rule `base_sha_dropped`
already states here: a marked value was stored and can be read back, a dropped token was not
stored at all, and a non-finite number means the producer's arithmetic went wrong upstream of
the request. Each is bounded at `MAX_UNKNOWN_BUCKETS` with a `_total` beside it, like every
other echo on this path, and every one is logged as well as returned.

### A second 500 that never reached the database

`changed_lines`, `diff_chars`, `max_diff_chars` and a finding's `line` are plain `int` fields
with no tolerant coercer, so a non-finite one **fails validation** — and FastAPI renders that
422 by quoting the offending input back into JSON, which cannot represent a `nan`. The refusal
itself then raised `ValueError: Out of range float values are not JSON compliant: nan` and the
request 500ed having never touched Postgres. Dropping a non-finite number to `None` before
binding closes both mechanisms; the value becomes "nobody said", which is what
`_count_or_none` and `_cost_or_none` already give an unbelievable figure.

### `POST /review/outcomes`, the sibling path, refuses instead

One bad byte in one `note` took the whole batch down there — the eleven good rows that
endpoint's entire design exists to keep. The remedy is different and the difference is that
endpoint's own stated rule: the panel must never fail a review because the board was fussy, so
ingest takes what it can read, while a fixer recording an outcome can simply be told. So a NUL
is **refused per item**, naming every field that held one, and the siblings still record. The
two values it would be worst to mark are exactly the ones this endpoint carries: `key` is a
defect identity matched with `==`, so a marked key names no finding at all, and `note` is the
evidence behind a refutation of the board's own judge. A NUL in the request-level `session`
is a 422, which is what an over-long one has always been, and for the reason given there — a
contact address that resolves to nothing is worse than none.

`POST /post` and the rest of the board carry the same class of defect and are **not** fixed
here: they are a different router with a different contract, and a fix that guessed at it
would be this issue's mistake in the other direction.
