# the seats now get the changed files' git history, and a `git log` question stops costing the round its stop

A code-reading seat has every file in the pull request and no history. `fetch_pr_tree`
materialises its checkout from GitHub's tarball endpoint, which is the right call for the
reasons its own docstring gives — it needs nothing of the local repository, and the local
checkout "is on whatever branch it was last left on and is never the PR's code" — but a
tarball carries no `.git`. Nor would one help: `READ_ONLY_TOOLS = ("Read", "Grep", "Glob")`
means the seat has no shell to run `git log` with, and packfiles are not something `Read`
answers questions from. So the seat declares a coverage gap, and every declared gap costs
the round its confident stop.

On the one instrumented cycle — lexray#1631, two rounds, 29 confirmed findings, eight
declared gaps — **three of the eight** were questions a single `git log` answers: whether a
constant landed a day after the migration it belongs to (it landed 74 minutes after, which
is the kind of error a day-granularity answer invites), whether a file had ever held
another exemption entry, and whether a frozen setting list matched the registry *as it
stood on 2026-07-14* rather than merely today. The seat had reasoned correctly to the edge
of what it could see and said so: *"they match today's registry, and without history the
two are indistinguishable."* **Zero** of the eight were closable by executing the repo's
suite, which is why #92 stays closed and this is the surviving class it asked for.

### `history_brief`, alongside `ci_brief`

The shape #91 and #548 already established: compute it once, centrally, from the trusted
side of the boundary, and put it in the prompt. `panel_scope.history_brief` reads the
**operator's own clone** at the ref the pull request NAMES — `base_sha` if this clone
carries it, else `origin/<base>`, else `<base>` — and renders, per changed file, how many
non-merge commits it has ever had, when it was first added, and its five most recent
commits with author dates to the minute in a single timezone so that two of them can be
compared without arithmetic.

Renames are followed on every read, and that is a correctness fix rather than a nicety.
`git log -- <path>` stops dead at the commit that renamed a file INTO that path, so a file
born as `old.py` and renamed last week reads as "2 commits, first added <the rename
commit>" — under a heading saying it is that file's history. That is a confident wrong
answer where the gap it replaced was an honest "I cannot tell", which is strictly worse,
and it is why the total is counted off a followed log rather than taken from `rev-list
--count`, which has no `--follow`: one entry may not carry a followed date beside an
unfollowed count.

Never the checkout's own HEAD. That is `fetch_pr_tree`'s argument arriving one seam over:
history read at whatever branch the box was left on is history of something else, rendered
under a heading saying it is history of the files under review — a plausible wrong answer,
which is worse than no answer.

**It executes nothing from the pull request.** It reads a local, trusted repository's
history: the safe side of #75's boundary, no cwd handed over, no convention file resolved,
no hook able to run. It is strictly smaller than #113, which already shipped.

**It fails closed and cheap.** No `cfg["path"]`, a PR this clone never fetched, a shallow
clone — whose graft would otherwise be reported as the commit that added every file, and
whose `rev-list --count` reports its own depth as a file's life — or no `git` at all: no
block, a `config_notes` line saying which, and the round proceeds exactly as it does
today. The same contract `fetch_pr_tree` keeps ("never raises") and `default_branch_rules`
keeps (`{}` on any failure).

**It is vendor-neutral, and that is the part that makes it better than widening code
access.** `SEAT_READS_CODE` is `frozenset({"claude"})` because three of the four vendors
cannot express "read but do not execute". On the measured cycle codex was `code_blind` in
both rounds and filed zero surviving findings, declaring gaps like "whether any non-test
callers still import `seed_platform_settings`" — a `grep` question from a seat with
nothing to grep. A prompt block reaches every seat regardless of vendor tooling, which no
extension of `reviewer_code_access` can do. The judge gets it on the same terms, because a
finding that rests on when a file changed is dismissed as unsupported by a party that
cannot check it.

### how much history, and what it costs the diff

The issue left this open (`-n 10` per changed file "is a guess", and "a diff touching 40
files would produce a lot of prompt for little value"). It is budgeted exactly as the claim
block is, on the same rule — **the block yields, the diff does not**: the ceiling is
`HISTORY_CHARS` (4,200) or one part in `HISTORY_BUDGET_SHARE` (8) of the tightest seat's
`max_diff_chars`, whichever is smaller, charged off the budgets as they stood *before* the
claim's own deduction so that two blocks each taking a share cannot compound. An eighth
against the claim's quarter, because the claim is the thing a seat TESTS the diff against
and history is context that makes certain questions answerable.

Within that: five commits per file rather than ten, and files richest-first by churn, so
the budget buys breadth over depth — a gap declared about a file absent from the block is
a gap this did not close, while the fifth commit down was already answering nothing. The
block says how many files did not fit, because a seat that read a budget decision as an
absence of history would be reaching the confident wrong answer this exists to prevent.

### what it does not do

It answers *when* a file changed. It does not answer what a file CONTAINED at an older
commit, which is what the third measured question actually needed — the general form of
that is a read-only `git show` capability, and it is a bigger change than a brief. The
block says so in as many words, so a seat still declares that gap instead of inferring the
contents from a subject line.

`review_panel.history_brief` (default **true**) and `panel.py --no-history-brief` turn it
off. That is not a thoroughness dial: #716's honest limit is n=1 on a single history-heavy
migration PR, and the way that stops being n=1 is running the same PRs both ways and
counting the declared gaps. The flag is the instrument rather than a convenience, for the
reason `--no-pr-claim` is: the dial lives in the repo under review, so producing the
control arm by editing it would change the diff whose gaps are being counted. Which arm a
round was in is a `config_notes` line rather than a column on `review_runs` — #550 argues
for the column, and it is a schema change this deliberately leaves to whoever runs the
comparison.
