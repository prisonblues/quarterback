# an agent asked to sort the plan can now do it

`plan_order` has always computed the order the facts imply and handed back the exact
payload that would apply it, ending with *"You cannot apply this."* So the answer went to
a person to re-enact by eye against a list of forty rows — and correcting an item's own
stale reasoning was equally out of reach, because `POST /plan/item/update` is gated the
same way.

`plan_reorder` and `plan_item_update` write through the **browser vhost** as the signed-in
person, using `QUARTERBACK_HUMAN_URL` and a new `QUARTERBACK_EDGE_COOKIE`. Neither is a new
credential class: this is the handshake `qb-doctor`'s `edge` check already probes, and the
cookie is a signed-in session. It has to be the browser host — `app/auth.py` notes that the
agent vhost strips `X-Edge-Auth`, so the same write aimed at the agent host cannot succeed
however it is authenticated.

Every way of not reaching a person is separated from an answer about the request. No URL or
no cookie refuses before spending a request and names which is missing; a forward-auth 302
is reported as a missing or expired session and never followed, since chasing it lands on a
login page that answers 200 and would look like success. A real 403 stays an HTTP error, so
callers can still tell *you may not* from *you are nobody*.

**This deliberately opens `app.auth.human` to any process running as the user** — the same
cookie satisfies `/dials`, `/plan/item/update`, scope declaration and `exempt`'s grant path.
That trade was taken knowingly and #479 is the standing record of what it covers and how it
is meant to be tightened: an undo, a scope-level interlock, cooling-off, and the
propose-vs-dispose shape `/plan/item/exempt` already implements.
