# a round now records which harness produced it

A run payload carried `judge_model`, per-reviewer `model`/`effort`/`max_diff_chars`/`truncated`/`duration_ms`/token usage, `diff_budgets`, `run_key`, `cycle`, `round`, `stop_reason`, `stop_veto` — a careful account of the electorate and of the decision — and nothing at all about the code that ran the panel. Checked against a real payload: zero keys matching `version|harness|commit|digest`.

`.harness-rules` argues at length that an unpinned reviewer MODEL makes *"codex found more than claude"* unattributable, and pins three of the four seats for exactly that reason. The harness itself was unpinned and unrecorded, and it changes far more often than a vendor slug.

On 2026-08-31 this repository merged six PRs that changed `round_stop`, `converged`, the `fix_injection` accounting and `restored_lines`, and added `guard_churn`. In the same week the deployed panel on one host was measured twice, two hours apart, and had been rebuilt underneath a running session in between — one run without #75's member sandbox and one with it, from the same session. Nothing in either record distinguished them.

So two rounds of one cycle can be read by materially different machinery, and the r1 → r2 comparison every stop argument in this system rests on silently assumes they were not.

### Four fields, and the split is the judgement

There is no single true answer to *"which harness produced this round"* available from inside a running panel, and `qb-doctor`'s `check_harness` had already written down why: the truthful answer lives in the flake pin's rev, no harness script can reach it — each one knows only its own store path — so that tool compares CONTENT and says in its own docstring that content is a proxy. This records both halves and labels which is which.

- **`harness_rev`** — the commit of the checkout the panel ran from. The only **authoritative** field: it names something a reader can go and `git show`. NULL on every *installed* harness, which is most of them, because the nix store is not a checkout. The panel reports it only when the containing repository actually TRACKS the panel's own file, so a scratchpad copy dropped inside some other checkout records NULL rather than that repository's HEAD — a plausible forty hex digits in the right column belonging to the wrong repository is the one outcome worse than an absence.
- **`harness_dirty`** — whether that checkout's loop directory carried changes the rev does not, untracked files included. This is what makes a rev honest rather than merely present: `panel-review-pr.md` tells you to run the panel from a scratchpad copy, and a dirty copy is the normal case for anybody developing it — this issue was found from one. NULL is "no rev, or nobody could ask", never a silent `false`.
- **`harness_digest`** — `loops-sha256-1:<hex>` over the loop modules. **A proxy.** It cannot name a version and cannot say which of two is newer. It is the only field that is always present and never wrong about the question an r1 → r2 comparison actually asks: same code, or not.
- **`harness_path`** — where it all ran from. **A locator**, machine-scoped: for a nix install it doubles as an exact identity of the build, and for a scratchpad copy it is the only field that says the round did not come from the deployed harness at all.

A field that is sometimes a lie is worse than three that are each honest about their scope, because a reader cannot see which of the two they have.

The identity is resolved **at import**, not when the payload is written. That is part of the answer rather than an implementation detail: a payload is written after the review, so a harness rebuilt in between would otherwise be recorded as the one that produced the round — and the rebuild lands on the `~/.claude/loops` symlink, so resolving `__file__` late would follow it to the new store path. The field would then hide precisely the event it exists to expose. Import costs about 8 ms against a round measured in minutes.

`harness_dirty` reads the same files the digest does — the top level of the loops directory, not `tests/` below it — so it means exactly "the digest is not what that rev would produce" rather than "somebody edited a test".

### No release number, and that is a finding rather than an omission

The issue proposed a release number as one of the candidates. `package.nix` ships `loops`, `commands`, `templates`, `claude`, `githooks` and the harness README into the store — not `pyproject.toml`, not `CHANGELOG.md` — and the release number is applied on the base after a merge by `scripts/release.py run`, so a harness built from a branch has never had one. A version string knowable from inside a running installed harness does not currently exist. It would also have been too coarse for the week that prompted this: all six of those merges would have shipped under one number.

### What the digest is, exactly

`*.py` in the loops directory, no deeper, each contributing its name, its length and its body with the shebang dropped, hashed in sorted order.

Every one of those is a claim rather than a convenience. `loops/tests/` ships with the package and does not run a round, so a release that only changed tests must not read as different machinery. The shebang is dropped because `package.nix`'s `postFixup` runs `patchShebangs` — counting it would give every deployed harness a digest matching no checkout anywhere, which is the drift `qb-doctor`'s `_same_but_for_shebang` once reported as 24 changed files on a host that had just rebuilt. Names and lengths are hashed beside the bodies so two modules cannot trade contents with the digest unmoved.

The scheme rides on the value rather than living in a docstring. A bare hex digest would go on comparing equal to itself after somebody changed what goes INTO it — silently splitting one harness version into two groups or merging two into one, which is this issue's own bug one layer down and in the direction nobody would notice. A change to what is hashed bumps the tag.

### Migration `mdef4716b`

`harness_rev`, `harness_digest` and `harness_path` are `Text`; `harness_dirty` is `Boolean`. All nullable, no server default, **no backfill**, no CHECK, no index.

The backfill would be the bug. The only value available to write is today's harness, and attributing today's version to rounds that ran under another is precisely the mixing these columns exist to make visible — and unlike a NULL, a wrong digest cannot be told from a right one afterwards. The round payload is a temp file on whatever host ran the panel, so a round that runs before these columns exist has lost its machinery version permanently: `m6bc45ff1`'s argument for `converged` and `m331126c7`'s for the provenance working, with a date on it, since #637 recalibrates `escalate_on.fix_injection` against a population of rounds being produced this week.

No CHECK because this board has no proposition about these values to enforce. It does not know what a store path looks like, does not know the digest scheme, and `harness_dirty: true` beside a null `harness_rev` is a shape the panel does not send today and might tomorrow — a constraint written against today's producer is a 500 waiting.

`harness_rev`, `harness_dirty` and `harness_digest` ride `GET /reviews` on `merge_base`'s rule: what a recalibration groups a population by must not cost one fetch per run. `harness_path` is detail-only — on a nix install it changes exactly when the digest does, so it buys no grouping the digest has not already bought, and what it is for is a reader who has picked one round and wants to go and look at the machinery.

### And a 500 in a neighbouring field, found while adding these

`_word_or_none` has coerced `scope` and `fix_range_source` since #647 and checked shape, blankness and length — not NUL. Postgres cannot store `\u0000` in a `text` column any more than in a JSONB string, and Python's `str` holds one happily, so `scope: "pr\u0000"` passed every check the module made and became a 500 at INSERT on a round with one bad character in it. That is the same class #643 and #647 each found on the JSONB side, on the scalar side where nobody had looked.

The two fields here share that coercer, so the check lands on all four at once. `tests/test_review_harness_identity.py` covers the inherited case by name.

### Detecting a mid-cycle change is deliberately not in this release

The issue's second half is that the deployed harness changes underneath running sessions. Recording the version per round is what makes that DETECTABLE; detecting it and warning is a separate decision, and the argument for splitting them is that its right home is genuinely contested. Panel-side it is a `round_stop` veto, which would change stop semantics in the same week #637 is recalibrating them. Board-side it is a derived flag, which `m6bc45ff1` argues at length against for `converged`. Nothing is lost by waiting: the DATA is what is unrecoverable, and a detector can be run over stored rows at any later date. Filed as its own issue.
