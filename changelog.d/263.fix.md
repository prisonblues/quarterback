# a context reset hands back the work the previous conversation was holding

`/clear` leaves a pane with a conversation that remembers nothing of the one before it, and
the claims and lease the previous conversation took stayed live under it — renewed by an agent
with no memory of taking them, where passive expiry could never reach them because nothing had
died.

The hook has had a backstop for this for a while and it could never fire. It looked the
previous conversation up in a file keyed on the INSTANCE, and an instance IS a conversation
unless an operator pinned one by hand — `qb-seats` unsets `QUARTERBACK_INSTANCE` and puts
nothing in its place (#540) — so on this fleet the record was per-conversation, could never
hold a different one, and the whole path no-op'd for every session that actually runs.

It is now keyed on the pane: the CLI process, which is the thing a `/clear` does not restart.
So a reset ends the conversation that was there, for an ordinary unpinned session and not only
for a hand-pinned seat — and it says which kind of ending it was. `qb-hook` had never read
`SessionStart`'s `source`, so every start looked alike, including the two that are opposites;
it now records `context_reset` when Claude Code says the previous conversation was cleared and
`superseded` when something else merely arrived.

The other half was the stamp. `POST /session/end` hands back the claims recorded against the
session it names, and a claim taken through `qb-mcp` was stamped with whatever conversation
that process was spawned with — so the release reached the first reset in a terminal and no
later one. The server reads the live conversation now (#146), so the stamp and the release
name the same thing again.

### What still hands nothing back

A resume, which is the same work continuing, and this is the failure that would be worse than
the bug. `SessionStart` fires for `resume` as well as for `clear`, and `--resume` reuses the
session id — but `/resume` inside a pane picks a different conversation and would otherwise
reach the release, so it is refused by name rather than left to arithmetic. A `compact` never
reaches it at all: it does not mint a new conversation — the entries after one keep the same
`sessionId` — so the pane already holds its own id. A `fork` does mint one, carries memory
forward, and is recorded as `superseded`, which claims only that a different conversation is
here now; an older Claude Code that sends no source at all lands in the same arm.

An operator's pinned seat keeps the older instance-keyed record as its fallback: a restart
gives it a new CLI process, so the pane is new and empty while the identity is deliberately
the same.
