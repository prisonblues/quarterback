# a reset conversation stops holding claims it cannot account for

`/new` and `/clear` give a pane a conversation with no memory of the one before it, while the
board state pinned to that pane was untouched — including every claim the previous
conversation took, still live, still renewing on every prompt. Passive expiry is the board's
whole answer to a holder that has gone, and it can never reach this one: nothing died, so
nothing lapses, and the claim looks maximally fresh precisely because the pane is busy with
something else. A peer running `claims()` saw a live claim on a healthy agent and correctly
concluded the work was covered; the plan reported the item held, by a named holder, and it was
being worked by nobody.

`/session/end` has released a session's claims since #277, but it releases them **by session
key** — and the key on the claim was whatever session id `qb-mcp` was spawned with, which
stops moving the first time the pane is cleared. So the release reached the first reset and no
later one: a claim taken by the second conversation in a pane carried the first conversation's
id and was unreachable by any ending. `qb-mcp` now reads the pane's current conversation per
call instead of trusting the environment it started with, so a claim is stamped with the
conversation that actually took it.

`qb-hook` also reads `SessionStart`'s `source` for the first time, so a reset is told apart
from a resume rather than inferred: `clear` ends the previous conversation as a
`context_reset`, and a `resume` — the same conversation continuing, and the case where
dropping claims would be this bug with the sign flipped — keeps everything it holds.

And a Task sub-agent no longer ends its parent's session. It has a session id of its own and
inherits its parent's pane name, so inside a seat every sub-agent launch read the seat's own
session out of the supersede record and handed back the claims the seat was still working.
