# remove-worktree and prune-worktrees now find a worker that was only detected

`create-worktree` names a repo's worker container from `worker.type`, falling back to what the repo's dependency files and `docker-compose.yml` mention (huey, rq or celery). The two teardown scripts did not detect: `remove-worktree` fell back to `"none"` and `prune-worktrees` to `""`. So for a worker that was detected rather than configured, `remove-worktree` could not remove its container by name once the worktree directory was gone, and `prune-worktrees` could not pair it with a dead worktree.

The rule now lives in one place, `worktree-worker`, which all three scripts source, so they cannot disagree. Before either teardown removes or reports a worker container by name, it checks that `docker compose` made it in that worktree, because huey's container prefix does not name the project and another repo's same-named branch has a worker of the same name. Without the library beside them, `create-worktree` refuses to run, while the two teardowns still run, look for no worker by name, and say so.
