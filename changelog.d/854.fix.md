# remove-worktree and prune-worktrees now find a worker that was only detected

`create-worktree` names a repo's worker container from `worker.type`, falling back to what the repo's dependencies say (huey, rq or celery). The two teardown scripts fell back to "none" instead. So for a worker that was detected rather than configured, `remove-worktree` could not remove its container by name once the worktree directory was gone, and `prune-worktrees` could not pair it with a dead worktree.

The rule now lives in one place, `worktree-worker`, which all three scripts source, so they cannot disagree. Without it beside them, `create-worktree` and `prune-worktrees` refuse to run, and `remove-worktree` still tears down but warns that it could find a worker container only through `docker compose`.
