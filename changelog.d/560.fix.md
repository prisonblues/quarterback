# a premise declared after its own fix pass is now recorded as one

The futility brake gets its whole value from running before the patch: `panel.py --premise` fires on the FIRST declaration that answers `--premise-decidable no`, and exit 4 means *do not write the fix*. Both that design and the fixer's brief assume the fixer is a separate agent an orchestrator briefs, so there is a moment between "decide the premise" and "start editing" for the brake to occupy. `panel-review-pr.md` recommends the configuration where that moment does not exist — with more than one PR, the per-PR agent runs the panel and then fixes, with nobody to brief — and there the premise gets declared against the round it followed, once the pass is written, committed and pushed. It still takes its veto on the next round, which is the late half; the early half, the only reason it fires on the first declaration, is unavailable.

Nothing could tell the two apart. An undeclared-then-declared pass and a declared-then-written pass produced byte-identical register entries, so a cycle where the brake was an annotation read exactly like one where it was a brake. On the cycle this was found on, the orchestrator gave the fixer no register path at all — `--premise` was uncallable during the fix pass — and the only reason anyone knows is that the fixer said so rather than inventing a path.

Each declaration now carries the commit the tree was sitting on when it was made. `--premise` reads it itself with `git rev-parse HEAD` in the directory the declaration is made from; it is not a flag, on the same rule that makes a `decidable: no` sticky — a fixer asked to supply the evidence against itself can supply the head it wishes it had, and in worktree mode the repo's canonical checkout is not the tree the patch lands in. A round then compares each stamp against the heads its own cycle recorded, and names in `config_notes` any declaration stamped with the head of a later round: the fix pass that premise explains was written, committed and pushed before the premise was, so exit 4 had nothing left to refuse. That is the shape the cycle this was found on produced, twice, and it has no innocent explanation.

It identifies positively or says nothing. A stamp matching no round's head — an unpushed local commit, an amend, a rebase, a declaration run from another directory — is left alone, because a check that accuses an honest fixer over ordinary history is one an orchestrator learns to skip past. It costs a round no subprocess and no network call: every commit id involved was already in the cycle's own payloads. And it is evidence rather than a rung. A stop taken here would be the late half again, and what was missing was never another way to end a cycle.

**The other half of the ordering is not checked, and the silence is a decision rather than a gap.** A patch written into the working tree and not yet committed moves no `HEAD`, so the declaration that follows it is stamped with its own round's head — the same value the honest declaration made before the first edit produces. Editing and then committing is the ordinary shape of a fix pass, so this is not a corner case. Two mechanisms were built for it and both were withdrawn. Asking whether the declaring tree was dirty accused any fixer whose checkout carried an unrelated modification, and fix-in-place mode permits exactly that. Comparing a fingerprint the round took against one the declaration took was better and still wrong twice: a concurrent agent in a shared checkout, an editor autosave or a background build moves the tree between the two readings with no fix pass involved, while a file already modified when the round ran fingerprints the same both times however much the fix pass then changes it. Hashing contents rather than status lines closes the second and leaves the first untouched, because the ambiguity is in the inference and not in the digest: a tree change cannot be attributed to a particular actor from evidence read in that actor's own environment. That is #622. Where the patch is uncommitted, the ordering is the fixer's discipline and both briefs now say so instead of implying a safety net.

`round_stop.premises` also says whether the round was handed a register at all. Without that, a cycle that never wired one and a cycle whose fixer skipped a declaration produce the same `undeclared_rounds` list — and the first is the one that actually happened. `wired: false` with rounds listed is a cycle whose reader was not even pointed at a register. It says nothing about whether the fixer was given that path or could write it — the round and the fix pass are separate invocations, and `declared` is the field that says somebody reached the register.

The two briefs say the rest. Where the orchestrator is also the fixer, the declaration belongs after reading `round_stop` and before the first edit, the register path is the agent's own to choose because nobody is going to hand it one, and the same path goes to every round's `--premise-file` — a register the round cannot read counts nothing.
