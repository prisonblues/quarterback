# a question waiting on a person was countable but not answerable

`POST /blockers/resolve` has two halves — a person ANSWERS, an agent may WITHDRAW a question
it raised itself — and across every row the live board held, the answering half had never
fired. All five resolutions were withdrawals.

The reason was in the UI rather than the trust model. The board's `⛔ N waiting` chip was an
`<a href="/plan/view">` whose tooltip read *"Answer on the plan page"*, and the plan page
offers its answer box as a chip on a plan ROW: `_human_blockers_for` attaches a blocker by
matching an OPEN item's forge ref. Correct on its own terms, and the composition is not — a
blocker whose subject nothing plans is counted on the board, pointed at the plan page, and
absent from it. It is also self-perpetuating, because the subject reaching a terminal state
is what closes the plan item, so the question stops being answerable at the moment somebody
answers it in life.

The chip is now the control for the queue it counts. It expands into the rows themselves —
class, subject (linked, for a PR or an issue carrying a repo), the question as text rather
than a tooltip, who asked, how long ago, and who is being asked — each with a box that posts
straight to `POST /blockers/resolve`. No plan row is in the path, because the missing plan
row is the defect and not a step. An empty answer is refused by the page for the plan page's
reason: the server's refusal is a 422 about a field, and an empty resolution is how "waiting
on a human" turns quietly back into a guess.

The plan page keeps its chip unchanged. A question that IS holding a row up should be
answerable on the row it is holding up; what was missing was the surface for the ones holding
nothing up.

Two things fell out of building it. The chip's tooltip read the oldest question's class off
`oldest["class"]` — the key `GET /plan` uses, where this read is `GET /blockers`, which sends
`kind` — so the one sentence a person saw before deciding whether to open the queue named the
class as `undefined`. And the count was fetched once at page load, so a board left open on a
desk showed the number it had when the tab was opened; it is now re-read on the same fifteen-
second beat as the sessions, and never while the list is open, because a poll landing
mid-sentence would take a half-written answer out from under somebody.

A third came out of the review: two answers in quick succession start two reads of the queue,
and if the first response landed second the list reverted to the state that still held the row
just resolved — an open answer box on a question the server had closed. Reads are numbered now
and the last one wins.
