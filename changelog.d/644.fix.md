# a green harness suite means the same thing locally as it does in CI

Two tests in `harness/tests/test_qb_dash.py` failed under `-n auto` and passed alone, in unrelated
worktrees, on branches that touch no dashboard code. Two more joined them since. The cost is not the
red run: it is that a real regression in this file reads as the known flake and gets waved through,
and that an agent which reruns until green learns to treat a red suite as noise. #621 and #626 are
heading toward a machine merging on a green suite, and a suite with a known-flaky file cannot carry
that.

There were two mechanisms, not one.

### `_click_row` failed open, so a timeout arrived wearing someone else's name

It waited for the pane to stop moving, and when the wait ran out it printed a line and **clicked
anyway**. The click then landed on the header, `ClickTable.on_click` refused it as `row: -1`, and the
failure surfaced hundreds of lines later as whatever verb the test was checking — "the hammer did not
start a fix". Four failures were investigated across two agents and two worktrees before anybody read
the `never settled` line in the captured output.

It now raises, naming the table, the offset, the row actually under the pointer, and the read budget
it exhausted. That is what `_click_row_index` twenty lines above it already did when the row it
wanted was off screen; this helper was the only one in the file that answered a question it could not
answer.

The budget is `_SETTLE_READS`, default **240** reads and settable with `QB_DASH_SETTLE_READS`. Stated
precisely, because the loose version overclaims: every unsuccessful read still costs a
`pilot.pause(0.05)`, so this is *also* a wall-clock floor — 12s where the old 60 reads were 3s — and
it still stretches under contention. What makes a count the right shape is not that it escapes time
but what it guarantees: a real deadline expires while the app is descheduled, so a loaded box buys
the pane fewer chances to settle exactly when it needs more, whereas a count guarantees 240
observations however long the scheduler takes to deliver them. The 4x is what makes that count large
enough to survive a loaded box. The loop leaves the moment two consecutive reads agree, so a healthy
run costs 0.1s whatever the ceiling is.

**And the raise is diagnostic, not remediation.** It does not make the flake less likely; it stops
the flake arriving under a false name. The reduction in failures comes from the opt-in below and from
the 4x budget — those are the two remediations, and separating them from the diagnostic is the
honest accounting.

### four tests read the live board, and the fleet writes to it while they run

`@needs_live_data` marks the four that click whatever the repo and the board actually have open
today. Three of the four failures anyone has recorded for this file are among those four tests, out
of 107 in it. Three of them already skip themselves when the board has nothing to click — "no PR row
on the board today", "no reviewable PR row", "no free issue-backed item on the plan" — which is the
file admitting the dependency in its own words.

They are now **opt-in**: `QB_DASH_LIVE=1`. Not deleted and not stubbed — they are the tests that found
the defects worth finding, and stubbing the data keeps the clicking and loses the point, which is
that the dashboard works on the board as it really is.

What this buys is that a local run means what CI's run means. CI already had the property: `tests.yml`
runs the dashboard suites serially, with no board configured, so these skip there and are meant to.
Anyone running `pytest harness/tests` on a box that *has* a board was getting a different suite from
the one CI gates on, and finding out by way of a failure attributed to whatever they had just
changed.

### what this does not fix

The live tests themselves are still a function of what the fleet is doing. Measured while writing
this, on unmodified `main` and an idle box, `test_the_hammer_starts_a_fix_and_the_rest_of_the_issue_row_opens`
failed once in three runs. That is the behaviour being moved out of the gating suite, not the
behaviour being repaired, and it is #678.
