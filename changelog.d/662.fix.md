# `.database.protect` names a family, not two names that go stale by Tuesday

`prune-worktrees` calls a database orphaned when no live worktree maps to it, and that
mapping is per-worktree (`<project>_<create-name>`). A database a project mints on any other
axis matches nothing and is offered for deletion on every single run.

The axis that actually comes up is the migration head. A test suite that copies each run's
database from a pre-migrated template — `<project>_test_tmpl_<head>`, ~45ms instead of
~1.5s — produces databases that belong to a *head*, not to a checkout, so the sweep has
always reported them as debris. `.database.protect` existed for exactly this and could not
express it: the lookup was `PROTECT["$db"]`, an associative-array subscript, so an entry had
to equal a database name character for character.

Naming them exactly is not a smaller version of the right answer, it is a different and
worse one. The live heads sit on branches — one on the integration branch, another on
whatever is unmerged — and **no single checkout can see all of them**, so the pinned list is
unverifiable from anywhere it could be asserted. Land a migration and it protects two dead
templates while the new live one goes back to being swept, silently and in the unhelpful
direction. It also drags per-branch state into a shared base-branch config file, which makes
editing `.worktree.json` a step in landing a migration.

Configured entries are now **glob patterns**. `myapp_test_tmpl_*` names the family, cannot go
stale, and leaves this script knowing nothing about anybody's migration tool. Literal entries
are unaffected — a pattern with no metacharacters is an exact match — and the two built-in
protections (`<project>`, `<project>_test`) stay exact, because those are names these scripts
mint themselves.

### The new failure mode is quieter than the old one, so it is reported

Staleness fails by protecting too little, which is noisy: the sweep offers you a database you
wanted kept. A pattern fails the other way — too broad, and it suppresses a *genuine* orphan
with nothing on screen to say so. So every configured match now prints under `Protected by
.database.protect`, with the pattern that caused it. The built-ins stay silent; there is
nothing to be surprised by about `<project>_test`.

### Two ways this could have looked like it worked

`[[ "$db" == $g ]]` needs `$g` **unquoted**. Quoted, `==` degrades to a literal string
comparison — which is the bug being fixed, and every literal entry keeps passing over it.
`test_a_wildcard_protects_the_whole_family` is the test that goes red for it; run against a
quoted variant it fails alongside four others while the six backward-compatibility tests stay
green, which is the shape of the trap.

The suite drives the real scan by extracting it from the script between markers, as
`test_prune_worktrees_claims.py` already does for the claim sweep. The first version of it
reproduced `postgres_container_candidates` by hand instead and simplified two greps into one,
so it answered a different question about container ordering than the script does. That is
now extracted too: a stub of the *answer* is fine, a hand-simplified copy of the *logic* is
how a suite goes green about code nobody runs.

hand-pinned list be kept honest from inside one checkout? — rather than patching around it
five separate times.
