# a checkout's claim can now be released by the session that works the tree

`create-worktree` takes the issue's claim for the MACHINE, with no session on it. That part is
right — the agent that will work in the tree does not exist yet, and stamping the creating session
locked the eventual worktree agent out of its own row — but nothing ever picked the claim up
afterwards. `POST /session/end` releases the claims a SESSION took and a null session matches none
of them; `qb-reconcile` looks the holder up in `/active`, which lists leases, so a bare machine
name could never appear there and the check was structurally incapable of settling. Nine such
claims stood on one box the day this was found, three of them naming issues that had closed seven
hours earlier, and only `qb-release` by hand or the 8h fuse could end one.

The claim is now handed over rather than re-attributed. The worktree's own `CLAUDE.local.md` tells
the agent that opens the tree to re-claim the same issue from inside its session, which the board
reads as a renew by the same machine: the row keeps its id, its history and its plan item, and
gains an owner that ending the session can find. `/fix-issue` and `/review-pr` carry the same step
for the routes they cover.

### And the check that could not settle one now can

The other half of the same failure, for the claims nobody adopts. `qb-claim --session ""` writes
a row whose holder is the bare machine, and every caller that takes a *lease* sends the key
header that composes `machine/agent-name` — so no lease in `/active` carries a bare machine name,
and looking one up there is not a hard case that came out unknown but a comparison with no
favourable answer available. `qb-reconcile` did it anyway, and explained the absence with the one
sentence that could not apply: that a working agent had gone quiet for half an hour between lease
renewals. Nine claims read that, every fifteen minutes, under `complete: false`.

Three of the nine named issues that had closed seven hours earlier, and the same report already
said so a few keys away under `done_candidate`. That fact is now read across: a claim over work
GitHub reports merged, or an issue it reports closed, is a stale claim — the item has outlived
its work and the claim outlived it with the item, whoever holds it. A claim a live session holds
is never promoted that way, because an agent's last turn happens with its own issue already
closed.

A machine claim over work that is still open stays an unknown, and now says what it is. Which
script took it comes from the note, because the remedy differs: `create-worktree` records
`worktree <create-name> on <host>` and that name is `remove-worktree`'s argument, while
`qb-start` takes the same kind of claim for routes with no worktree at all, where naming
`remove-worktree` would send a reader at a command that cannot release it. Nothing here releases
a claim.

### A settled claim does not take the plan row that settled it

`POST /plan/reconcile` stores one row per `(repo, ref_kind, ref_value)` and keys a request's
findings under "last one wins". A `stale_claim` settled by its item's own `done_candidate` is on
that ref by construction and is reported after it, so it would take the row — and `plan_read`'s
caveat would stop saying the work is already finished and go back to offering the item as next,
on the very rows this change exists for. It says nothing the `done_candidate` does not, the two
being one fact said twice, so it is not sent at all and the plan write is unchanged from before
this condition existed. A claim that was stale on its own evidence is an observation and keeps
its row, exactly as before.

The wider question — that list order decides which condition a ref stores whenever any two land
on one ref, and that ranking them makes the stored condition depend on which checks could reach
GitHub — predates this and is #768.
